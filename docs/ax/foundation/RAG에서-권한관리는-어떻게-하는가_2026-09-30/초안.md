사내 RAG를 열어두면 예상보다 빨리 이런 질문을 받습니다.

> "이거 아무나 검색하면 다 나오는 거예요?"

인사팀 평가 문서, 미공개 계약서, 임원 보고 자료가 같은 인덱스에 있다면 답은 "예"입니다.
그리고 이 질문에 프롬프트로 답하려는 팀이 의외로 많습니다.

**RAG 권한 문제의 핵심은 하나입니다. 보안은 LLM 에게 부탁하는 것이 아니라 검색 단계에서 막는 것**입니다.

> Security should be enforced before generation.

이 글은 기업 AI 도입 보안에서 가장 먼저 부딪히는 RAG 권한관리를, 프롬프트가 왜 안 되는지부터 실제로 어떻게 막는지까지 정리합니다.

---

## 왜 프롬프트로는 안 되는가

시스템 프롬프트에 "사용자가 보면 안 되는 정보는 말하지 마"라고 적는 팀을 자주 봅니다. 결과부터 말하면 이걸로는 **충분하지 않습니다.**

이유는 순서에 있습니다.

- 검색은 **이미 벡터 공간에서 끝났습니다.** LLM이 답을 만들기 전에, 접근 권한이 없는 문서 조각이 이미 검색 결과로 뽑혀 있습니다
- 결과만 나중에 지우는 방식으로는 "몇 건이 나왔다", "이런 종류의 문서가 있다" 같은 **정보 자체를 못 막습니다.** 내용을 가려도 존재 여부가 새어 나갑니다
- 원본을 새 시스템으로 복사해 오면 원본 시스템에서 일어난 **권한 변경이 인덱스에 반영되지 않습니다.** 그룹웨어에서 권한을 회수해도 RAG 인덱스에는 어제 권한이 그대로 남습니다

프롬프트는 LLM의 출력을 조정할 뿐, 검색이라는 앞 단계에서 일어난 일을 되돌리지 못합니다. 그래서 권한은 **검색 이전**에 걸어야 합니다.

## 권한이 걸려야 하는 위치 — 검색 앞단

전체 흐름을 그리면 이렇습니다.

```text
사용자 → 인증 → Role 확인 → 접근 가능 문서 결정
→ 허용된 문서 안에서만 검색 → 답변
```

"Role 확인 → 접근 가능 문서 결정"이 검색보다 앞에 있다는 점이 핵심입니다. 사용자가 볼 수 있는 문서 범위를 먼저 정하고, 그 범위 **안에서만** 벡터 검색과 키워드 검색이 돌아야 합니다. 검색 결과를 다 뽑아놓고 걸러내는 순서가 아닙니다.

관련 · [건설 AI 적용 사례 5가지 — 지식허브부터 입찰 리스크까지](/ax/construction/construction-ax-5-ai-agents/)에서도 통합 지식허브의 색인 단계에 "권한 기반 Indexing"을 넣은 이유가 같습니다.

## 방법 1 — RBAC(Role-Based Access Control)

가장 기본적인 방법은 역할별로 접근 가능한 문서 범위를 미리 정의하는 것입니다.

| Role | 접근 가능 문서 |
|---|---|
| 일반 직원 | 일반 사규 |
| 팀장 | 일반 사규 + 팀 문서 |
| HR | 인사 관련 문서 |

이 표가 실제로 하는 일은 단순합니다. 로그인한 사용자의 Role을 확인하고, 그 Role에 매핑된 문서 집합만 검색 대상으로 넘깁니다. 나머지 문서는 애초에 검색 인덱스 조회 범위에 들어오지 않습니다.

## 방법 2 — 문서 Metadata 필터링

Role만으로 부족한 경우가 있습니다. 같은 팀장이라도 프로젝트별로, 보안 등급별로 접근이 달라야 할 때입니다. 이럴 때는 문서 조각 하나하나에 메타데이터를 붙입니다.

```text
department = HR
security_level = confidential
project = A
```

Retrieval 단계에서 이 값으로 걸러냅니다. 벡터 검색은 "의미가 비슷한 조각"을 찾지만, 그중에서 사용자의 department·security_level·project 조건에 맞는 조각만 후보로 남기는 방식입니다. RBAC가 큰 틀의 문이라면, 메타데이터 필터링은 그 안에서 조각 단위로 거는 자물쇠에 가깝습니다.

## 자주 나오는 질문

**퇴사자 계정은 어떻게 되나요.** 계정을 비활성화하는 순간 Role 확인 단계에서 걸립니다. 원본 시스템과 권한을 연동해 두었다면, 퇴사자가 보던 문서는 별도 재색인 없이 즉시 검색 대상에서 빠집니다. 반대로 원본을 복사해서 인덱스를 따로 관리하고 있다면 이 연동이 끊겨 있을 가능성이 큽니다.

**문서 권한이 바뀌면 인덱스는요.** 원본 시스템에서 권한이 바뀌었는데 인덱스가 옛 권한을 들고 있으면, 지금까지의 권한 설계가 전부 무의미해집니다. 그래서 원본을 복제하지 않고 연결하는 구조가 중요합니다. 복제하면 이 동기화를 직접 구현하고 계속 유지해야 합니다.

**감사로그에는 무엇을 남기나요.** 최소한 누가, 언제, 어떤 질문으로, 어떤 문서 조각에 접근했는지가 남아야 합니다. 접근이 거부된 시도도 함께 남겨야 나중에 "이 사람이 이 문서를 보려 한 적이 있는가"를 추적할 수 있습니다.

## 근거 — 설계 단계에서부터 요구사항으로 넣은 경우

건설사 A와의 프로젝트에서는 통합 지식허브를 설계하면서 RBAC와 감사로그를 처음부터 요구사항으로 정의했습니다. 그룹웨어·ERP·파일서버에 흩어진 문서를 하나의 검색 인덱스로 묶는 구조였는데, 원가·계약·법무처럼 민감한 문서가 섞여 있었기 때문에 "누가 무엇을 볼 수 있는가"를 색인 설계보다 먼저 정하고 구조에 반영했습니다. RAG보다 권한 모델을 먼저 고민해야 한다는 판단이 여기서 나왔습니다.

## 체크리스트

RAG 권한관리를 설계할 때 아래를 확인하면 프롬프트로 막으려는 시도를 미리 막을 수 있습니다.

- [ ] 권한 확인이 검색보다 **앞에** 있는가 (검색 후 필터링이 아닌가)
- [ ] Role별 접근 가능 문서가 표나 문서로 정의돼 있는가
- [ ] 보안 등급·프로젝트 단위로 더 세밀한 필터링이 필요한 문서가 있는가
- [ ] 원본 시스템의 권한 변경이 인덱스에 실시간 또는 준실시간으로 반영되는가
- [ ] 원본을 복제하지 않고 연결하는 구조인가
- [ ] 접근 거부 시도까지 감사로그에 남는가
- [ ] 퇴사·직무 변경 시 인덱스 접근 권한이 계정 상태와 함께 즉시 바뀌는가

권한 설계는 나중에 되돌리기 가장 어려운 부분입니다. RAG 파이프라인은 하루 만에 다시 만들 수 있어도, 잘못된 권한으로 한 번 새어 나간 정보는 인덱스를 지워도 이미 본 사람의 기억에서 지워지지 않습니다. RAG 구축 절차 전체와 다른 실패 지점은 [RAG 구축 절차와 실패 지점](/ax/foundation/rag-build-process-and-failures/)에서 더 다뤘습니다.
