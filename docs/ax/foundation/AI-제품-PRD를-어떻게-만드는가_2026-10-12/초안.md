AI 기능을 넣은 제품의 PRD(제품 요구사항 정의서)를 써 본 사람이라면 한 번쯔음 같은 경험을 합니다. 기존에 쓰던 PRD 양식을 그대로 들고 왔는데, 뭔가 빠진 느낌이 들지만 정확히 뭐가 빠졌는지는 설명하기 어려운 경험입니다.

**일반 PRD 와 AI 제품 PRD 의 결정적 차이는 결과가 deterministic 하지 않다는 점입니다.**

```text
일반 기능   버튼 클릭 → 항상 A
AI 기능     Input → Model → 확률적인 Output
```

일반 기능은 같은 입력을 주면 같은 결과가 나옵니다. 버튼을 누르면 항상 같은 화면으로 넘어가고, 같은 조건이면 항상 같은 금액이 계산됩니다. 그래서 일반 PRD는 "무엇을 만든다"를 정의하는 데 집중해도 충분합니다.

AI 기능은 다릅니다. 같은 입력이라도 모델의 응답은 매번 조금씩 다를 수 있고, 가끔은 완전히 틀린 답을 내놓기도 합니다. 그래서 "무엇을 만든다"만으로는 부족합니다. **어떻게 판정하고, 실패하면 어떻게 하는지**를 PRD 안에 같이 적어야 합니다. 이 글은 강의 제작을 돕는 AI 제품(Lecture Builder)의 PRD를 작성하면서 실제로 부딪혔던 질문들을 정리한 것입니다.

## 한눈에 보는 핵심 결론

| | 내용 |
|---|---|
| **일반 PRD가 보는 것** | 기능이 무엇을 하는가 (Input → Process → Output) |
| **AI PRD가 더 보는 것** | 그 결과가 맞는지 어떻게 판단하고(Evaluation), 틀렸을 때 뭘 하는지(Exception) |
| **놓치기 쉬운 항목** | 사람 확인이 필요한 지점(Human Review), 개선 근거가 되는 기록(Logging) |
| **가장 흔한 실패** | 정확도 목표는 적었지만 측정 방법이 없고, 실패 화면이 정의되지 않은 PRD |

## IPO 에 두 가지를 더한다

기획 문서를 쓸 때 흔히 쓰는 틀은 Input · Process · Output, 줄여서 IPO입니다. 무엇을 넣고(Input), 무엇을 하고(Process), 무엇이 나오는지(Output)를 적는 방식입니다.

AI 기능을 정의할 때는 여기에 두 가지를 더해야 합니다. **Evaluation**(잘했는지 어떻게 판단하는가)과 **Fallback**(실패하면 어떻게 하는가)입니다. 이 두 항목을 추가하면 AI 기능 정의가 눈에 띄게 좋아집니다. 이유는 간단합니다. IPO만 적으면 "정상적으로 작동했을 때" 이야기만 남고, AI가 확률적으로 틀리는 경우에 대한 답이 PRD 바깥에 남겨지기 때문입니다.

실제로 쓸 때는 Evaluation과 Fallback을 각각 더 쪼개는 것이 유용합니다. 그래서 저는 다음 9개 항목으로 AI PRD를 구성합니다.

| 항목 | 정의할 것 |
|---|---|
| Problem | 무슨 문제인가 |
| User | 누가 쓰는가 |
| Input | AI 에게 무엇을 주는가 |
| Process | AI 가 무슨 작업을 하는가 |
| Output | 어떤 형태로 돌려주는가 |
| **Evaluation** | 잘했는지 어떻게 판단하는가 |
| **Exception** | 실패하면 어떻게 하는가 |
| **Human Review** | 사람 확인이 필요한가 |
| **Logging** | 어떤 데이터를 남기는가 |

앞의 다섯 개(Problem, User, Input, Process, Output)는 일반 PRD에서도 쓰는 항목입니다. 뒤의 네 개가 AI 제품 PRD에서 추가로 필요한 항목입니다.

## 요구사항을 검증 가능하게 쓰는 법: Evaluation

가장 흔한 실패 지점은 **정확도 목표만 적고 측정 방법을 안 적는 것**입니다. "정확도 90% 이상"이라고만 쓰면 누가 어떤 데이터로 어떻게 측정했는지가 빠져 있어서, 출시 전에도 출시 후에도 그 숫자가 맞는지 아무도 확인할 수 없습니다.

Evaluation 항목에는 최소한 다음을 적어야 합니다.

- 정상 사례, 예외 사례, 치명적 오류 사례를 포함한 평가셋이 있는가
- 무엇을 "맞았다"고 판정하는 기준인가 (사람이 보고 판정하는가, 규칙으로 자동 판정하는가)
- 치명적 오류는 전체 오류율과 별도로 추적하는가

예를 들어 강의 자료를 요약하는 기능이라면 "요약이 원문의 핵심을 담고 있는가"만으로는 검증 가능하지 않습니다. "원문에 없는 내용을 추가했는가"(치명적 오류), "핵심 개념 중 몇 개를 포함했는가"(품질 지표)처럼 판정 가능한 기준으로 나눠야 합니다.

## 실패 시 동작을 정의하는 법: Exception

두 번째 실패 지점은 **실패 시 동작이 없어서 장애 때 아무 화면도 안 나오는 것**입니다. 일반 기능은 실패하면 에러 메시지 하나로 충분한 경우가 많습니다. AI 기능은 "실패"의 종류가 더 다양합니다. 모델이 응답을 못 주는 경우, 응답은 왔지만 형식이 깨진 경우, 형식은 맞지만 내용이 근거 없이 틀린 경우가 전부 다른 처리를 필요로 합니다.

Exception 항목에서는 이렇게 나눠서 적는 것이 좋습니다.

- 모델이 타임아웃되거나 응답을 못 줄 때 → 재시도 또는 사용자에게 지연 안내
- 응답 형식이 깨졌을 때 → 재요청 또는 이전 결과 유지
- 내용이 근거 없이 틀렸을 가능성이 있을 때 → 사용자에게 검토 요청 또는 결과 보류

이 세 경우를 구분하지 않고 "오류 시 재시도"라고만 적으면, 실제로는 형식 오류와 내용 오류를 똑같이 재시도로 처리하게 되어 같은 실수가 반복됩니다.

## 사람 확인이 필요한 지점: Human Review

AI 기능이라고 해서 모든 결과를 AI가 바로 사용자에게 보여줘야 하는 것은 아닙니다. Human Review 항목은 **어디까지는 AI가 바로 내보내고, 어디부터는 사람이 확인한 뒤 내보내는지**를 정합니다.

이 경계를 정하는 기준은 결과가 틀렸을 때의 피해 크기입니다. 강의 초안을 만드는 기능이라면 사용자 본인이 바로 검토하므로 즉시 노출해도 괜찮을 수 있습니다. 반면 다수에게 배포되는 콘텐츠를 만드는 기능이라면 배포 전에 담당자 확인을 거치는 단계가 필요합니다. 이 기준은 누가 틀린 결과에 책임을 지는가라는 질문과 이어지는데, 그 책임 구분을 더 자세히 다룬 글이 [AI 에이전트 시대, 산업 전문가와 IT 전문가는 어떻게 역할을 나눠야 하는가](/ax/foundation/role-split-domain-and-it/)입니다. 그 글의 기준을 그대로 가져오면, PRD에서 Human Review 경계를 정할 때도 "결과를 되돌릴 수 있는가, 외부 고객에게 직접 영향을 미치는가"를 먼저 물어야 합니다.

## 개선 근거를 남기는 법: Logging

세 번째 실패 지점은 **로깅 항목이 없어서 나중에 개선 근거를 못 만드는 것**입니다. AI 기능은 출시 시점의 완성형이 아니라, 운영하면서 계속 고쳐야 하는 기능입니다. 무엇을 고칠지 판단하려면 데이터가 있어야 합니다.

Logging 항목에는 최소한 다음이 들어가야 합니다.

- Input과 Output 원문 (개인정보·민감정보는 마스킹 처리)
- Evaluation 판정 결과 (맞았는지, 어떤 종류의 오류였는지)
- Exception이 발생한 경우 어떤 분기를 탔는지
- Human Review를 거쳤다면 사람이 수정했는지, 그대로 승인했는지

이 네 가지가 있으면 "어떤 유형의 입력에서 오류가 자주 나는가", "사람이 자주 고치는 부분은 어디인가"를 사후에 분석할 수 있습니다. 반대로 이 로그가 없으면 AI 기능은 출시 이후 블랙박스가 되고, 체감상 느려지거나 틀려도 원인을 특정할 방법이 없습니다.

## AI PRD 작성 체크리스트

실제로 PRD를 쓸 때는 다음 체크리스트로 9개 항목이 모두 채워졌는지 확인합니다.

- [ ] Problem과 User를 한 문장으로 설명할 수 있는가
- [ ] Input에 AI가 받는 데이터의 형식과 범위가 명시되어 있는가
- [ ] Output의 형식(텍스트, 구조화 데이터, 파일 등)이 정의되어 있는가
- [ ] Evaluation에 정상·예외·치명적 오류를 구분한 평가셋이 있는가
- [ ] Exception에 오류 유형별로 다른 동작이 정의되어 있는가
- [ ] Human Review 경계가 피해 크기 기준으로 정해져 있는가
- [ ] Logging에 입력·출력·판정 결과·사람 수정 여부가 포함되어 있는가

이 체크리스트에서 하나라도 빈칸이 있다면, 그 항목은 "나중에 정하죠"가 아니라 PRD 리뷰 단계에서 바로 채워야 합니다. AI 기능은 출시 후에 Evaluation과 Logging 없이 운영하면, 문제가 생겨도 무엇이 문제인지조차 알 수 없는 상태로 흘러가기 쉽습니다.

## 결론

일반 PRD와 AI 제품 PRD의 차이는 결과가 deterministic 한가 아닌가에서 시작합니다. 이 차이 때문에 AI PRD는 Input·Process·Output만으로 끝나지 않고, 그 결과를 어떻게 판정하는지(Evaluation), 틀렸을 때 무엇을 하는지(Exception), 사람이 어디까지 확인하는지(Human Review), 무엇을 기록해 둘지(Logging)까지 같이 정의해야 합니다.

정확도 목표만 적고 측정 방법을 비워두거나, 실패 시 동작을 적지 않거나, 로깅 항목을 빠뜨리는 것은 PRD가 아직 완성되지 않았다는 신호입니다. 이 9개 항목을 채우는 것이 AI 제품 PRD를 쓰는 가장 구체적인 출발점입니다.
