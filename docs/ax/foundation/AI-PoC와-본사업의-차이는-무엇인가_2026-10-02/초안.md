"PoC는 성공했는데 본사업으로 못 넘어갑니다." 여러 회사에서 비슷한 말을 듣습니다.

데모는 잘 돌았습니다. 담당자도 만족했습니다. 그런데 막상 예산을 받아 본사업으로 넘기려는 순간 멈춥니다. 이 현상을 기술 문제로 보면 원인을 못 찾습니다.

**PoC와 본사업은 같은 프로젝트의 앞·뒤 단계가 아니라, 단계마다 묻는 질문 자체가 다릅니다.**

| 단계 | 질문 |
|---|---|
| **PoC** | 기술적으로 가능한가 |
| **Pilot** | 제한된 실제 환경에서도 작동하는가 |
| **Production** | 회사 시스템으로 지속 운영할 수 있는가 |

PoC를 통과시킨 질문과 본사업을 통과시켜야 하는 질문이 다르기 때문에, PoC 통과가 본사업 통과를 보장하지 않습니다. 이 글은 그 차이가 구체적으로 어디서 생기는지, 그리고 PoC를 설계할 때 무엇을 봐야 본사업에서 덜 엎어지는지를 정리합니다.

## PoC에서 본사업으로 가면 무엇이 늘어나는가

PoC 단계에서는 담당자가 엑셀을 Python으로 분석해도 결과만 맞으면 됩니다. 운영 중인 시스템을 건드리지 않고, 샘플 데이터 몇 개로 "이게 가능한가"만 보여주면 되기 때문입니다.

본사업으로 넘어가면 같은 로직 하나를 돌리는 데도 다음이 전부 필요해집니다.

```text
API · DB · 보안 · 로그인 · 권한 · 개인정보 · 로그
관리자 화면 · 장애처리 · SLA · 비용 · 모니터링
```

PoC에서는 이 중 거의 없어도 됩니다. 본사업에서는 이 중 하나라도 빠지면 "정확도는 좋은데 운영할 수 없는 시스템"이 됩니다. 늘어나는 것은 AI 로직이 아니라 **그 로직을 회사 시스템 안에서 안전하게 반복 실행시키는 구조**입니다.

## PoC가 통과했는데 본사업에서 엎어지는 이유

현장에서 반복해서 보는 전형적인 실패 지점은 네 가지입니다.

- **운영 주체가 정해지지 않음** — Prompt와 Knowledge Base는 누가 관리하는가. PoC는 만든 사람이 계속 들고 있어도 되지만, 본사업은 그 사람이 자리를 비워도 돌아가야 합니다.
- **기존 시스템 연동 공수를 과소평가** — PoC에서는 데이터를 추출해서 분석하면 되지만, 본사업에서는 기존 시스템에 실시간으로 붙어야 합니다. 이 연동 공수가 PoC 전체 기간보다 더 걸리는 경우가 많습니다.
- **평가셋이 없어 "좋아졌다"를 증명하지 못함** — PoC에서는 몇 개 예시로 "그럴듯하다"는 인상을 주면 충분합니다. 본사업 예산을 받으려면 무엇이 기준이고 무엇이 개선인지를 숫자로 보여줘야 하는데, 이 기준 자체가 없는 경우가 많습니다.
- **정확도는 올랐는데 사용자 행동이 바뀌지 않음** — 모델 지표가 좋아져도 담당자가 기존 방식을 그대로 쓰면 본사업 전환의 근거가 사라집니다. 결과가 좋아 보이는 것과 업무가 바뀌는 것은 다른 문제입니다.

네 가지 모두 AI 성능과는 무관합니다. 운영·조직·증명의 문제입니다. 그런데 이 네 가지는 PoC 보고서에는 거의 등장하지 않습니다. PoC 보고서는 "무엇이 가능했는가"를 쓰는 문서이고, 저 네 가지는 "그래서 누가, 어떻게 계속 돌릴 것인가"에 대한 답이기 때문입니다. 질문 자체가 다른 문서에 속해 있으니, PoC를 아무리 잘 써도 본사업 심사에서 다시 물어보게 됩니다.

여기서 흔히 생기는 오해가 하나 있습니다. "PoC에서 이미 잘 됐으니 본사업은 그걸 확장만 하면 된다"는 가정입니다. 그러나 확장은 규모를 키우는 일이 아니라 **없던 기능을 새로 추가하는 일**입니다. 로그인도, 권한도, 장애 대응도 PoC에는 없었던 것이기 때문에 '확장'이 아니라 '신규 구축'에 가깝습니다. 이 인식 차이가 본사업 일정과 예산을 과소평가하게 만드는 가장 큰 원인입니다.

## 사례로 보면: 판별 로직에서 운영 체계로

건설사 B에서는 하자접수 데이터 약 5만 건을 두고, 고객이 요구한 중복·재접수·재발 구분이 가능한지를 검토하는 단계를 거쳤습니다. 이 단계의 질문은 단순합니다. "기존에 쌓인 데이터로 이 구분이 기술적으로 가능한가."

같은 업무를 본사업으로 확장하면 흐름 자체가 달라집니다.

```text
신규 접수 → AI 분석 → 유사 접수 제시 → 담당자 확인
→ 상태 변경 → 결과 저장 → 학습/평가 데이터 활용
```

PoC 단계의 질문은 "구분이 되는가" 하나였지만, 본사업 단계의 질문은 훨씬 많습니다. 담당자가 AI 제시 결과를 확인하는 화면은 누가 만드는가, 상태 변경은 기존 하자관리 시스템과 어떻게 동기화되는가, 저장된 결과를 다음 학습에 쓰려면 개인정보는 어떻게 처리하는가. 여러 현장을 연결하면 현장별 발생률, 입주 경과기간별 비교, 반복 유형, 공종별 문제, 처리 리드타임까지 보는 **운영 체계**로 범위가 넘어갑니다. PoC 단계의 판별 로직 하나로는 이 범위를 감당할 수 없습니다.

## PoC 성공 기준을 어떻게 잡아야 본사업에서 덜 엎어지는가

PoC 성공 기준을 "모델이 잘 맞혔다"로 잡으면 본사업 심사에서 다시 처음부터 증명해야 합니다. 그래서 PoC를 설계할 때부터 다음을 같이 정해두는 것이 낫습니다.

- **운영은 누가 하나요** — PoC를 만든 사람이 아니라, 본사업이 시작되면 Prompt·Knowledge Base·예외 처리를 매일 들여다볼 사람을 미리 정합니다.
- **비용은 어디서 늘어나나요** — 모델 호출 비용보다 연동·보안·모니터링·장애처리 쪽에서 더 늘어납니다. PoC 견적에는 이 항목이 아예 없는 경우가 많습니다.
- **본사업에서 새로 생기는 요구사항은** — 위에 적은 API·권한·로그·SLA 목록을 PoC 기획 단계에서 한 번이라도 짚어두면, 본사업 전환 때 "이걸 왜 지금 알았냐"는 상황을 줄일 수 있습니다.

이 세 질문에 지금 답할 수 없다면, 그것 자체가 신호입니다. PoC를 더 잘 만드는 것으로는 해결되지 않고, 조직이 아직 본사업을 받을 준비가 안 됐다는 뜻입니다. 이때는 PoC를 반복하기보다 운영 주체를 먼저 지정하는 쪽이 순서상 맞습니다. 이 앞단 준비 상태를 포함한 전체 단계 구분은 [AX 전환 로드맵 — 실패 비용으로 나누는 5개 관문](/ax/foundation/ax-transformation-roadmap/)의 0관문에서 더 자세히 다뤘습니다.

## 체크리스트 — 본사업 전환 전에 확인할 것

- [ ] Prompt·Knowledge Base를 운영할 담당자가 정해져 있다
- [ ] 기존 시스템 연동 범위와 공수를 PoC 단계에서 한 번 짚었다
- [ ] "좋아졌다"를 증명할 평가셋이 있다
- [ ] 담당자의 업무 방식이 실제로 바뀌는지 확인할 방법이 있다
- [ ] API·보안·권한·로그·SLA·모니터링 비용을 견적에 포함했다

다섯 개 중 두세 개만 비어 있어도 본사업 단계에서 걸릴 가능성이 높습니다.

## 마지막으로

PoC가 통과했다는 것은 "기술적으로 가능하다"는 것만 증명한 상태입니다. 본사업은 그 가능성을 회사 시스템 안에서 매일 반복시킬 수 있는가를 묻습니다. 질문이 다르면 통과 기준도 다르고, 책임 주체도 달라집니다.

PoC를 기획하는 시점에 이미 본사업의 질문 — 운영은 누가, 비용은 어디서, 증명은 무엇으로 — 을 한 번씩 짚어두는 조직과 그렇지 않은 조직은, PoC가 똑같이 성공해도 그 다음부터 갈립니다.
