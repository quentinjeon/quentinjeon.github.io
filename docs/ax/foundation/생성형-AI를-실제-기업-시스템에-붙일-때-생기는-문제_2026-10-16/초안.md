생성형 AI를 사내 시스템에 붙여보겠다는 프로젝트는 대부분 모델 선택에서 시작합니다.
어느 모델이 더 정확한지, 어떤 프롬프트가 더 잘 먹히는지를 먼저 비교합니다.

그런데 실제로 프로젝트를 몇 달 진행해보면 막히는 지점은 거의 모델이 아닙니다.
**모델이 틀린 답을 내는 문제보다, 그 모델을 기업 시스템 안에 안전하게 넣는 운영 문제가 훨씬 많이 생깁니다.**
여기서 생성형 AI 도입 사례의 깊이가 갈립니다.

이 글은 건설·에너지·커머스를 포함한 여러 도메인에서 AX 프로젝트를 진행하며 반복해 마주친 문제를, 특정 회사 성과가 아니라 **공통으로 나타나는 패턴**으로 정리한 것입니다.

> **이 글의 범위**
> 모델 비교나 프롬프트 기법이 아니라, 기업 시스템에 AI를 붙일 때 운영 측면에서 공통으로 생기는 문제와 그 대응 방향을 다룹니다.

## 모델보다 먼저 막히는 아홉 가지 지점

생성형 AI를 기업에 도입하는 방법을 고민할 때 가장 먼저 봐야 하는 표입니다. 아래 아홉 가지는 모델을 아무리 잘 골라도 저절로 풀리지 않습니다.

| 영역 | 실제로 생기는 문제 |
|---|---|
| **데이터** | 사내 문서 자체가 틀렸거나 중복돼 있습니다. AI가 틀린 게 아니라 원본이 틀린 경우가 많습니다 |
| **권한** | 사용자마다 볼 수 있는 데이터가 다릅니다. 검색 결과를 걸러내는 것만으로는 막을 수 없습니다 |
| **연동** | AI 혼자서는 업무를 끝낼 수 없습니다. ERP·CRM·그룹웨어를 읽고 써야 끝이 납니다 |
| **안정성** | LLM API 오류와 timeout이 발생합니다. 재시도와 대체 경로가 없으면 업무가 그대로 멈춥니다 |
| **지연** | 답변이 20초 걸리면 직원은 다시 담당자에게 물어봅니다 |
| **비용** | 사용량이 늘수록 토큰 비용이 커집니다. 파일럿 때 계산한 단가로는 전사 확산을 감당하지 못합니다 |
| **평가** | 모델이나 프롬프트를 바꾸면 전체를 다시 검증해야 합니다. 평가셋이 없으면 좋아졌는지도 모릅니다 |
| **규정** | 개인정보·내부기밀이 모델 호출 과정에 섞여 나갈 수 있습니다 |
| **변화 관리** | 기능이 좋아도 직원이 쓰지 않으면 실패입니다. 가장 과소평가되는 항목입니다 |

이 중 앞의 다섯 가지를 조금 더 자세히 보겠습니다.

## 데이터 — AI가 아니라 원본이 틀렸다

사내 RAG를 열어보면 "답변이 이상하다"는 피드백이 먼저 들어옵니다. 원인을 추적해보면 모델이 아니라 **원본 문서가 중복되거나 개정 전 버전이 섞여 있는 경우**가 훨씬 많습니다. 규정은 공지로 덮여 있고, 견적서는 버전이 여러 개 떠 있고, 같은 내용이 부서별로 다르게 적혀 있습니다.

이 상태에서 AI를 먼저 붙이면 **답변은 그럴듯한데 틀린 문서를 근거로 답하는 상황**이 반복됩니다. 데이터 정리가 모델 튜닝보다 먼저입니다.

## 권한 — 걸러내는 방식으로는 부족하다

가장 늦게 발견되고 가장 크게 터지는 문제입니다. 사용자마다 볼 수 있는 문서와 시스템이 다른데, 검색 결과를 나중에 걸러내는 방식으로는 **"이런 문서가 몇 건 있다"는 정보 자체가 이미 새어나간 뒤**입니다.

실제로는 조각 단위로 접근 권한을 붙여 색인하고, 원본 시스템의 권한이 바뀌면 그 변화가 즉시 반영돼야 합니다. ERP·그룹웨어·CRM에 걸려 있는 권한 체계를 복사해서 새 시스템으로 옮기는 순간, 원본의 권한 변경은 더 이상 따라오지 않습니다. 이 구조를 AI Agent의 실행 권한까지 확장한 내용은 [AI 사원증과 AI Workforce Control Plane](/ax/foundation/ai-workforce-control-plane/)에서 더 다뤘습니다.

## 연동 — AI 혼자서는 업무가 끝나지 않는다

AI가 답변을 잘하는 것과 업무가 끝나는 것은 다릅니다. 재고를 조회하고 구매요청을 올리고 결재를 요청하는 일은 결국 **ERP·CRM·그룹웨어 같은 레거시 시스템을 읽고 써야** 끝이 납니다.

여기서 생성형 AI 도입 방법이 갈립니다. 레거시 시스템을 갈아엎는 쪽이 아니라, 기존 시스템은 그대로 두고 그 위에 AI가 안전하게 접근하는 연동 계층을 얹는 쪽이 현실적입니다. 에너지 도메인에서는 설비 이력이 엑셀에, 작업허가가 종이에 흩어져 있던 상태에서 이 연동을 먼저 설계했습니다. 자세한 구조는 [에너지업계 AX, 챗봇보다 먼저 설계해야 하는 것](/ax/energy/energy-ax-integrated-operations/)에 정리했습니다.

## 안정성과 지연 — 20초 걸리면 안 쓴다

LLM API는 종종 응답하지 않거나 timeout이 납니다. 재시도 로직과 대체 경로 없이 이 오류를 그대로 사용자에게 노출하면, 직원은 두 번 겪고 다시는 쓰지 않습니다.

지연도 같은 문제입니다. 답변이 20초 넘게 걸리면 "그냥 담당자한테 물어보는 게 빠르다"는 말이 바로 나옵니다. 캐싱, 단계별 응답, 처리 중 상태 표시 같은 장치가 모델 품질보다 체감 만족도에 더 크게 영향을 줍니다.

## 비용과 평가는 어떻게 다루나

비용은 파일럿 단계의 계산이 전사 확산에서 그대로 깨지는 대표적인 지점입니다. 사용자가 10명일 때 괜찮던 토큰 비용이 1,000명으로 늘어나면 자릿수가 달라집니다. 그래서 처음부터 **요청당 비용을 추적하고, 캐싱과 모델 등급을 업무 중요도에 따라 나누는 구조**를 넣어야 합니다. 모든 요청에 가장 비싼 모델을 쓸 필요는 없습니다.

평가는 더 조용히 방치되는 문제입니다. 프롬프트나 검색 설정을 바꾸면서 "좋아진 것 같다"는 느낌으로만 판단하면, 실제로는 나빠진 부분을 놓칩니다. 질문·근거·정답을 함께 가진 평가셋을 작게라도 만들어 두고, 바꿀 때마다 같은 기준으로 다시 돌려봐야 합니다.

## 가장 과소평가되는 것 — 변화 관리

기능이 아무리 좋아도 직원이 쓰지 않으면 실패입니다. AX 프로젝트는 결국 세 가지를 같이 봐야 합니다.

```text
Technology + Process + People
```

기술만 보면 "좋은 시스템인데 아무도 안 쓰는" 결과가 나옵니다. 실패는 보통 이 세 지점에서 생깁니다.

- [ ] 파일럿 사용자만 쓰고 확산이 멈춘다
- [ ] 기존 업무 절차를 바꾸지 않고 도구만 얹는다
- [ ] 담당자가 바뀌면 시스템이 사라진다

세 번째가 특히 자주 보입니다. 파일럿을 만든 사람만 구조를 이해하고 있으면, 그 사람이 자리를 비우는 순간 시스템은 서서히 방치됩니다. 역할을 나누는 기준과 조직에 남기는 방법은 [AI 시대 역할 분담 — 산업 전문가와 IT 전문가](/ax/foundation/role-split-domain-and-it/)에서 다뤘습니다.

## 정리 — 기업에 AI를 붙일 때 실제로 어려운 것

지금까지 나온 질문에 짧게 답하면 이렇습니다.

| 질문 | 짧은 답 |
|---|---|
| 기업에 붙이면 뭐가 어렵나요 | 모델이 아니라 데이터·권한·연동·운영입니다 |
| 가장 자주 막히는 지점은 | 권한(걸러내기만으로는 부족)과 레거시 연동입니다 |
| 지연과 비용은 어떻게 다루나요 | 캐싱·모델 등급 분리·요청당 비용 추적으로 통제합니다 |
| 직원이 안 쓰면 어떻게 하나요 | Technology·Process·People을 같이 보고, 조직에 남는 구조로 설계합니다 |

이 아홉 가지를 단계별로 어느 순서로, 어떤 통과 기준으로 풀어야 하는지는 [AX 전환 로드맵 — 실패 비용으로 나누는 5개 관문](/ax/foundation/ax-transformation-roadmap/)에서 정리했습니다.

생성형 AI 도입 사례가 데모에서 멈추는 이유는 대부분 모델이 아니라 이 운영 문제들 중 하나입니다. 모델을 고르기 전에, 이 아홉 가지 중 몇 개가 지금 조직에서 이미 막혀 있는지부터 점검하는 편이 순서상 맞습니다.
