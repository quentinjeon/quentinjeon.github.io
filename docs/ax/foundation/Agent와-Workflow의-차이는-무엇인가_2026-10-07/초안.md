"이것도 에이전트고 저것도 에이전트다"라는 말을 자주 듣습니다. 순서대로 API를 호출하는 자동화 스크립트도 에이전트라고 부르고, 매번 다른 경로로 답을 찾아가는 시스템도 에이전트라고 부릅니다. 이름이 같아지면 설계도 섞입니다. 그래서 먼저 정의부터 분리해야 합니다.

> **Workflow는 사람이 절차를 정의하고, Agent는 AI가 상태를 보고 다음 Action을 선택합니다.**

이 한 문장이 이번 글의 전부입니다. 나머지는 이 문장이 실무에서 왜 중요한지, 그리고 왜 대부분의 기업에는 둘 중 하나가 아니라 그 중간 형태가 필요한지를 풀어낸 내용입니다.

## Workflow와 Agent, 그림으로 보면

Workflow는 사람이 미리 그려놓은 그래프를 따라갑니다. 분기는 있지만 그 분기 조건도 사람이 정해둔 것입니다.

```text
Workflow   문의 → 분류 → FAQ 검색 → 답변 → 종료
```

Agent는 매 단계마다 상태를 보고 다음 행동을 스스로 고릅니다. 이 루프가 바로 ReAct류 Agent Loop의 핵심입니다.

```text
Agent      State → Reasoning/Policy → Action 선택 → Tool → Observation → 다음 Action
```

겉으로 보면 둘 다 "입력을 받아서 처리하고 결과를 낸다"는 점에서 비슷해 보입니다. 하지만 결정권이 어디에 있는지가 다릅니다. Workflow는 설계 시점에 사람이 결정권을 다 써버립니다. Agent는 실행 시점에 결정권을 모델에게 넘깁니다. 이 차이가 비용, 감사 가능성, 실패 시 복구 방법을 전부 다르게 만듭니다.

## 실제로는 그 중간이 많다 — Bounded Agent

문제는 완전 자율 Agent를 기업 업무에 그대로 투입하기는 어렵다는 점입니다. 모델이 매번 "알아서" 다음 행동을 고르게 두면, 같은 입력에 대해 다른 경로로 처리될 수 있고, 사후에 왜 그렇게 처리했는지 재구성하기도 어려워집니다.

그래서 현실적인 형태는 완전 자율도 아니고 고정 절차도 아닌 **Bounded Agent**입니다. 허용된 Action Space를 먼저 정해두고, 그 범위 안에서만 모델이 판단하게 하는 방식입니다.

```text
ANSWER · SEARCH · ASK_CLARIFICATION
ESCALATE · CREATE_TICKET · CHECK_ORDER
```

모델은 이 여섯 개 중 하나를 고르는 일만 합니다. 새로운 행동을 즉석에서 만들어내지 않습니다. 이렇게 하면 모델의 판단력은 그대로 쓰면서도, 실행 가능한 범위는 사람이 설계 시점에 고정할 수 있습니다.

## Action Space는 어떻게 정하나

Action Space를 정하는 기준은 "이 업무에서 실제로 반복되는 결과가 몇 가지인가"입니다. 고객 문의 대응이라면 결국 답변하거나, 추가 정보를 묻거나, 사람에게 넘기거나, 티켓을 만드는 정도로 좁혀집니다. 이 목록을 만들 때 다음 질문이 유용합니다.

- 지금 사람이 수동으로 처리할 때, 선택지는 실제로 몇 가지인가
- 되돌릴 수 없는 행동(결제, 발송, 데이터 변경)과 되돌릴 수 있는 행동(조회, 질문)을 구분했는가
- 목록에 없는 상황이 오면 무엇을 하는가 — 기본값은 반드시 "사람에게 escalation"이어야 한다

세 번째가 특히 중요합니다. Action Space는 "이 안에서만 움직여라"가 아니라 "이 안에 없으면 멈추고 사람을 불러라"로 설계해야 합니다. 그래야 목록이 완벽하지 않아도 사고로 이어지지 않습니다.

## 언제 Agent를 쓰고, 언제 Workflow로 충분한가

여기서 흔한 실패가 생깁니다. Workflow로 충분한 일에 Agent를 끼워 넣는 경우입니다. 입력과 출력이 고정되어 있고 분기가 몇 개로 끝나는 업무라면, Agent는 비용과 지연만 늘립니다. 모델 호출 한 번마다 시간과 비용이 들고, 같은 입력에 대해 다른 경로로 처리될 여지까지 생기기 때문입니다.

| 질문 | Workflow | Bounded Agent |
|---|---|---|
| 분기 조건을 미리 다 나열할 수 있는가 | 가능 | 어려움 |
| 입력마다 필요한 정보 조합이 달라지는가 | 아니오 | 예 |
| 처리 경로가 매번 똑같아야 감사에 유리한가 | 예 | Action 단위 로그로 보완 |
| 예외가 전체의 절반 가까이 되는가 | 아니오 | 예 |

표의 왼쪽 두 칸에 "예"가 많이 모이면 Workflow로 충분합니다. 예외가 많고 매번 다른 정보를 조합해야 판단이 서는 업무일수록 Bounded Agent 쪽으로 넘어갈 이유가 생깁니다.

## 실행을 재현할 수 있는가 — 상태를 코드로 강제하기

Agent를 도입했을 때 가장 자주 나오는 실패 지점은 상태 전이를 그림으로만 그리고 코드로 강제하지 않는 경우입니다. 다이어그램에는 "여기서는 승인 후에만 다음 단계로 간다"고 그려놓고, 실제 구현에서는 모델이 그 제약을 그냥 건너뛸 수 있게 열어두는 식입니다.

이 문제를 다루려면 상태를 등급별로 나누고, 등급마다 변경 규칙을 다르게 둬야 합니다. 관찰이나 진행률처럼 자주 바뀌는 상태와, 권한이나 하드 제약처럼 함부로 바뀌면 안 되는 상태를 같은 방식으로 다루면 안 됩니다. 이 구조화된 상태 설계는 [이전 글에서 다룬 상태·권한 모델](/labs/agent-level-agents-rl-governance/)과 그대로 이어집니다. Action Space를 정의하는 일과, 그 Action이 건드릴 수 있는 상태의 등급을 나누는 일은 사실 같은 작업의 양면입니다.

## 관점의 전환: 무엇을 말할 것인가에서 무엇을 해야 하는가로

Workflow 중심으로 설계하면 질문은 보통 "사용자에게 무엇을 말할 것인가"입니다. 대화의 다음 대답을 고르는 문제로 보는 것입니다. Agent, 특히 Bounded Agent 중심으로 설계하면 질문이 바뀝니다. **"이 상태에서 시스템이 무엇을 해야 하는가"**로요.

이 전환이 작아 보이지만 설계에 미치는 영향은 큽니다. 대답을 고르는 문제로 보면 자연스럽게 프롬프트와 대화 흐름 쪽으로 설계가 쏠립니다. 다음 행동을 고르는 문제로 보면 상태, 권한, 로그 쪽으로 설계가 쏠립니다. 후자가 감사와 재현이 필요한 기업 업무에 더 맞는 질문입니다.

## 체크리스트

- [ ] Action Space를 목록으로 적어봤는가 (적을 수 없다면 아직 범위가 넓은 것이다)
- [ ] 목록에 없는 상황의 기본 행동이 "사람에게 escalation"으로 정해져 있는가
- [ ] 되돌릴 수 없는 Action과 되돌릴 수 있는 Action을 구분했는가
- [ ] 상태 전이 제약이 다이어그램이 아니라 코드로 강제되는가
- [ ] 지금 업무가 Workflow로 충분한지 먼저 검토했는가

## 마무리

Agent와 Workflow는 둘 중 하나를 고르는 문제가 아닙니다. 대부분의 기업 업무는 분기가 명확한 부분은 Workflow로 두고, 예외와 판단이 몰리는 부분만 Bounded Agent로 좁혀서 맡기는 조합이 됩니다. 중요한 것은 "AI가 알아서 판단하게 둘지"가 아니라, **판단의 범위를 얼마나 명시적으로 정의하고, 그 범위 바깥으로 나갔을 때 무엇을 할지를 미리 정해뒀는지**입니다.
