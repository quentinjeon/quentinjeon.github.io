**AI 프로젝트 견적을 개발 기간만으로 잡으면 거의 틀립니다. 비용은 모델 호출이 아니라 주변에서 납니다.**

"기업 AI 도입 비용"을 검색해보면 나오는 결과는 대부분 "월 100달러부터 25만 달러까지" 같은 넓은 범위뿐입니다. 경쟁 콘텐츠가 전부 벤더 홍보물이기 때문에 숫자만 있고 **그 숫자가 어디서 나오는지**는 설명하지 않습니다. 이 글은 숫자 대신 견적을 쪼개는 항목 구조를 보여드립니다. 구조를 알면 어느 프로젝트에 대입해도 비용이 어디서 커질지 스스로 가늠할 수 있습니다.

## 왜 개발 기간만으로는 틀리는가

AI 프로젝트를 "모델을 붙이는 일"로 보면 견적은 개발 기간과 LLM 도입 비용, 즉 API 호출 비용으로 수렴합니다. 문제는 PoC와 본사업의 비용 구조가 다르다는 점입니다. PoC는 정제된 샘플 데이터로 모델이 잘 답하는지만 보면 됩니다. 본사업은 그 모델을 실제 업무 흐름 안에 넣어야 하고, 흐름 안에는 모델이 아닌 부분이 훨씬 더 많습니다.

LLM 호출 비용은 사용량이 늘어날수록 커지지만, 그조차 전체 견적에서 변수의 일부일 뿐입니다. 견적이 틀리는 이유는 API 비용을 잘못 계산해서가 아니라 **API 비용이 아닌 항목을 견적에서 통째로 빼놓기 때문**입니다.

## 비용이 실제로 나오는 자리

같은 규모의 프로젝트라도 아래 다섯 항목에서 공수가 예상을 벗어나는 경우가 많습니다.

| 항목 | 왜 커지나 |
|---|---|
| **데이터 준비** | 엑셀 20개에 흩어져 있고 형식이 다르면 정리부터 해야 합니다 |
| **시스템 연동** | ERP·CRM·TMS 연결은 예상보다 공수가 큽니다 |
| **AI 평가** | 모델 호출이 아니라 평가셋과 검증 프로세스를 만드는 일입니다 |
| **보안** | SSO·RBAC·감사로그 요구가 뒤늦게 들어옵니다 |
| **운영** | Prompt·Knowledge Base를 누가 관리할지 정해야 합니다 |

다섯 항목 모두 모델 자체와는 거리가 멉니다. 그런데 실제 견적서에서는 이 다섯이 "기타"나 "협의 사항"으로 뭉쳐져 한 줄로 처리되는 경우가 흔합니다. 뭉쳐진 한 줄은 본사업 중간에 터집니다.

## 견적을 8개 항목으로 나누는 이유

범위를 넓게 뭉쳐서 설명하면 고객도 공급사도 무엇에 돈을 쓰는지 알기 어렵습니다. 아래처럼 쪼개면 설명이 명확해집니다.

```text
Discovery · Data · AI · Application
Integration · Infrastructure · QA · Operation
```

- **Discovery** — 업무를 정의하고 입력·출력·정답 기준을 합의하는 단계입니다. 여기를 생략하면 뒤의 모든 항목이 다시 추정치가 됩니다
- **Data** — 흩어진 데이터를 모으고 정제하고 권한을 정리합니다. 실제 공수가 가장 자주 과소 산정되는 항목입니다
- **AI** — 모델 선택과 프롬프트·RAG 구성입니다. 사용량에 따라 LLM 도입 비용이 여기서 변동합니다
- **Application** — 사용자가 실제로 쓰는 화면과 흐름입니다
- **Integration** — ERP·CRM·TMS 등 기존 시스템과 연결하는 작업입니다
- **Infrastructure** — 서버·네트워크·보안 인프라를 준비합니다
- **QA** — 평가셋을 만들고 검증 프로세스를 돌리는 단계입니다
- **Operation** — 서비스를 넘긴 뒤 누가 운영할지 정하는 항목입니다

여덟 항목 중 어느 하나라도 견적에서 비어 있다면, 비어 있는 그 항목이 나중에 추가 비용으로 돌아옵니다.

## 운영(Operation)을 빼놓으면 본사업에서 반드시 문제가 된다

**운영을 빼놓고 견적을 내면 본사업에서 반드시 문제가 됩니다.** Prompt와 Knowledge Base는 한 번 만들고 끝나는 산출물이 아니라 업무가 바뀔 때마다 고쳐야 하는 자산입니다. 고치는 역할을 공급사가 맡는지, 고객사 내부 인력이 맡는지를 견적 단계에서 정하지 않으면 서비스가 열린 뒤 양쪽 다 "누가 할 일이냐"로 충돌합니다.

이 문제는 견적만의 문제가 아니라 AX 전환 전체 로드맵에서 조직이 시스템을 넘겨받는 단계와 같은 질문입니다. [AX 전환 로드맵 — 4단계 그림 말고, 실패 비용으로 나누는 5개 관문](/ax/foundation/ax-transformation-roadmap/)에서 다룬 4관문의 통과 기준도 "만든 사람이 자리를 비워도 다른 사람이 규칙을 읽고 고칠 수 있는가"였습니다. 운영 항목이 견적에 있다는 것은 그 질문에 답할 사람을 미리 정해두었다는 뜻입니다.

## 견적에서 자주 틀리는 세 지점

실제로 분쟁이 나는 지점은 대개 세 곳으로 좁혀집니다.

- 모델 API 비용만 계산하고 사용량 증가를 반영하지 않습니다. 사용자가 늘면 LLM 도입 비용도 같이 늘어난다는 전제가 견적에 없으면 예산이 중간에 바닥납니다
- 데이터 정리 공수를 "고객이 주겠지"로 가정합니다. Data 항목이 견적에서 가장 비어 있는 경우가 많은 이유이기도 합니다
- 평가 없이 넘겼다가 검수 단계에서 분쟁이 납니다. QA 항목 없이 진행하면 "잘 되는 것 같다"는 느낌만으로 검수를 통과시켜야 하는데, 느낌은 계약서에 쓸 수 없습니다

## 데이터 정리는 누가 하나요

견적 단계에서 가장 많이 나오는 질문입니다. 답은 "일단 공급사가 맡되, 범위를 Data 항목으로 명시한다"입니다. 범위를 명시하지 않으면 공급사는 정제된 데이터를 전제로 견적을 내고, 고객사는 원본 그대로 넘기면 되는 줄 아는 상태에서 프로젝트가 시작됩니다. 두 전제가 부딪히는 지점이 바로 엑셀 20개가 서로 다른 형식으로 흩어져 있는 순간입니다.

## 운영 비용은 어떻게 잡나요

운영 비용은 "완료 후 유지보수"가 아니라 **별도 항목으로 견적에 포함**해야 합니다. Prompt·Knowledge Base 수정 빈도, 담당 인력, 모니터링 범위를 Discovery 단계에서 합의해두면 Operation 항목의 공수를 구체적인 숫자로 바꿀 수 있습니다. 합의 없이 넘어가면 운영 비용은 계약 종료 후 "별도 협의"라는 이름의 공백으로 남습니다.

## 견적 작성 전 확인할 체크리스트

- [ ] Discovery 단계에서 업무의 입력·출력·정답 기준을 문서로 남겼는가
- [ ] Data 항목에 데이터 정제 공수가 별도로 계산되어 있는가
- [ ] AI 항목의 비용이 사용량 증가 시나리오를 반영하는가
- [ ] QA 항목에 평가셋 구축과 검증 프로세스가 포함되어 있는가
- [ ] Operation 항목에 운영 담당자와 수정 주기가 명시되어 있는가

## 정리

견적이 틀리는 이유는 숫자를 잘못 계산해서가 아니라 **계산해야 할 항목 자체가 빠졌기 때문**입니다. Discovery·Data·AI·Application·Integration·Infrastructure·QA·Operation 여덟 항목으로 나눠보면, 모델 호출 비용은 전체에서 작은 조각이고 나머지가 견적의 본체라는 게 드러납니다. 견적서에 "기타"로 뭉쳐진 줄이 있다면, 그 줄을 먼저 펼쳐보는 것이 산정의 시작입니다.
