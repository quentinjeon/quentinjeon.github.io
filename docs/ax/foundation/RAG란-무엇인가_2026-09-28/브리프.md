## 한 문장 정의

RAG(Retrieval-Augmented Generation)는 **LLM이 학습된 기억만으로 답하지 않고, 질문과 관련된 외부 정보를 먼저 검색해 그 결과를 Context 로 넣어 답하게 하는 방식**이다.

기업에서 특히 중요한 이유는 단순하다. LLM 은 그 회사의 최신 사규·내부 매뉴얼·계약서·제품자료를 **원래 모른다.**

## 실제 동작

사용자 관점:

```text
질문 → 전처리 → 관련 문서 검색 → 관련성 선별
→ 질문 + 문서를 LLM 에 전달 → 답변 생성 → 출처 표시
```

시스템 관점:

```text
Document → Chunking → Embedding → Indexing
Query → Query Embedding → Retrieval → Re-ranking → Context 구성 → Generation
```

## 왜 문서를 통째로 넣으면 안 되는가

| 이유 | 설명 |
|---|---|
| 비용 | 문서가 수백~수천 개면 매번 전부 Context 에 못 넣는다 |
| 정확도 | 관련 없는 정보가 많으면 LLM 이 중요한 정보를 놓친다 |
| 최신성 | 재학습 없이 문서만 갱신해도 새 정보가 반영된다 |

## 실패 지점

RAG 에서 결과를 가르는 건 LLM 이 아니라 **검색**이다.
문서를 잘못 가져왔는데 "이 자료를 기준으로 답하세요"라고 하면, LLM 은 틀린 자료를 **아주 그럴듯하게** 정리한다.

실제 쟁점은 이쪽이다.

- Chunk 를 어떻게 나누는가
- 표를 어떻게 처리하는가
- 제목과 본문의 관계를 어떻게 보존하는가
- Top-K 를 몇 개 가져오는가
- Keyword Search 와 Vector Search 를 같이 쓸 것인가
- Re-ranking 을 쓸 것인가

## 근거로 쓸 경험

**건설사 A** — 내부 기준을 자연어로 질의하는 챗봇을 기획하며, 단순 LLM 답변이 아니라 내부 문서를 검색해 답하는 RAG 형태가 필요하다고 판단. 기업 환경이라 검색 품질뿐 아니라 **권한과 감사로그**까지 함께 설계해야 했다.

> 쓸 때 주의 — 구현하지 않은 부분은 "설계했다 / 요구사항으로 정의했다" 로 쓴다.
