"RAG"라는 말은 이제 어디서나 나옵니다. 그런데 정작 "그래서 RAG가 뭔데요"라고 물으면
답이 사람마다 조금씩 다릅니다. 벡터 DB를 쓰는 것이라고 말하는 사람도 있고,
사내 챗봇 자체를 RAG라고 부르는 사람도 있습니다.

**RAG(Retrieval-Augmented Generation)는 LLM이 학습된 기억만으로 답하지 않고,
질문과 관련된 외부 정보를 먼저 검색해 그 결과를 Context로 넣어 답하게 하는 방식**입니다.

기업에서 특히 중요한 이유는 단순합니다. LLM은 그 회사의 최신 사규·내부 매뉴얼·계약서·제품자료를
**원래 모릅니다.** 학습 시점 이후에 생긴 문서는 물론이고, 애초에 외부에 공개된 적 없는
내부 자료는 아무리 큰 모델이라도 알 방법이 없습니다. RAG는 이 간극을 "재학습" 대신
"검색"으로 메우는 접근입니다.

이 글은 튜토리얼처럼 코드를 따라 치는 글이 아닙니다. RAG가 정확히 무엇이고,
어떻게 동작하며, **오히려 RAG를 쓰지 말아야 하는 경우는 언제인지**까지 정리한 정의형 글입니다.
실제 구축 절차와 기업 환경에서 터지는 실패 지점은 별도로 정리해 뒀으니,
구현 단계로 바로 넘어가고 싶다면 [RAG 구축 절차와 실패 지점](/ax/foundation/rag-build-process-and-failures/)을
먼저 봐도 됩니다.

## RAG 뜻 — 왜 "검색 증강"인가

Retrieval-Augmented Generation을 그대로 풀면 "검색으로 증강된 생성"입니다.
여기서 핵심은 두 단어입니다.

- **Retrieval(검색)** — 질문이 들어오면 관련 있어 보이는 문서 조각을 먼저 찾습니다
- **Generation(생성)** — 그 조각을 근거로 LLM이 답을 씁니다

즉 RAG는 LLM 자체를 바꾸는 기술이 아닙니다. LLM이 답하기 **전에** 검색이라는 단계를
하나 끼워 넣고, 그 검색 결과를 Context로 제공하는 구조입니다. 모델 파라미터를 건드리지
않기 때문에 파인튜닝보다 훨씬 빠르게 적용할 수 있고, 문서만 갱신하면 새 정보가 반영됩니다.

## 실제 동작 — 사용자 관점과 시스템 관점

사용자에게 보이는 흐름은 단순합니다.

```text
질문 → 전처리 → 관련 문서 검색 → 관련성 선별
→ 질문 + 문서를 LLM에 전달 → 답변 생성 → 출처 표시
```

그 뒤에서 시스템은 두 개의 파이프라인을 나눠서 돌립니다.

```text
Document → Chunking → Embedding → Indexing
Query → Query Embedding → Retrieval → Re-ranking → Context 구성 → Generation
```

용어를 하나씩 풀면 이렇습니다.

- **Chunking** — 문서를 통째로 검색하지 않고, 검색·비교가 가능한 작은 단위로 자르는 작업입니다
- **Embedding** — 텍스트를 의미가 비슷할수록 가까운 위치에 놓이는 숫자 벡터로 바꾸는 작업입니다
- **Retrieval** — 질문 벡터와 가까운 Chunk를 찾아오는 검색 단계입니다
- **Re-ranking** — Retrieval이 가져온 후보를 다시 한번 정밀하게 정렬해, 상위 일부만 남기는 단계입니다
- **Metadata** — 문서의 출처·버전·작성일·접근권한처럼, Chunk 본문 외에 검색과 필터링에 쓰는 부가 정보입니다
- **Context** — 실제로 LLM에 넣어주는, Retrieval과 Re-ranking을 거쳐 추려진 최종 근거 묶음입니다
- **Citation** — 답변이 어느 문서·어느 구절을 근거로 했는지 표시하는 출처 정보입니다

## 왜 문서를 통째로 넣으면 안 되는가

"그냥 문서를 전부 프롬프트에 넣으면 안 되나요"라는 질문을 자주 받습니다.
작은 문서 몇 개라면 가능합니다. 하지만 문서가 많아지면 세 가지 문제가 같이 옵니다.

| 이유 | 설명 |
|---|---|
| 비용 | 문서가 수백~수천 개면 매번 전부 Context에 못 넣습니다 |
| 정확도 | 관련 없는 정보가 많으면 LLM이 중요한 정보를 놓칩니다 |
| 최신성 | 재학습 없이 문서만 갱신해도 새 정보가 반영됩니다 |

RAG는 이 중에서도 특히 "필요한 것만 골라 넣는다"는 문제를 푸는 접근입니다.
문서 전체가 아니라, 질문과 관련된 일부만 매번 새로 골라 Context에 넣습니다.

## RAG 구축이란 — 결국 검색 품질의 문제

**RAG 구축이란, 이 파이프라인 전체를 회사 문서와 회사 질문에 맞게 조정하는 일**입니다.
그리고 결과를 가르는 건 LLM이 아니라 **검색**입니다.

문서를 잘못 가져왔는데 "이 자료를 기준으로 답하세요"라고 하면, LLM은 틀린 자료를
**아주 그럴듯하게** 정리해서 돌려줍니다. 겉보기엔 자연스러운 답변이라 오히려 더 위험합니다.

실제 구축에서 쟁점이 되는 지점은 이쪽입니다.

- Chunk를 어떻게 나눌 것인가
- 표를 어떻게 처리할 것인가
- 제목과 본문의 관계를 어떻게 보존할 것인가
- Top-K를 몇 개 가져올 것인가
- Keyword Search와 Vector Search를 같이 쓸 것인가
- Re-ranking을 쓸 것인가

이 각각을 어떻게 판단하고, 기업 환경에서 무엇이 실제로 문제를 일으키는지는
[RAG 구축 절차와 실패 지점](/ax/foundation/rag-build-process-and-failures/) 글에서 단계별로 다룹니다.
이 글에서는 정의를 넘어서는 구현 디테일은 다루지 않습니다.

## 언제 RAG를 쓰지 말아야 하는가

RAG를 설명하는 글은 많은데, "RAG를 쓰지 않아도 되는 경우"를 짚는 글은 드뭅니다.
아래에 해당한다면 RAG부터 시작하는 게 오히려 비효율일 수 있습니다.

- **참조할 외부 지식이 애초에 필요 없는 작업** — 문장을 다듬거나, 코드를 리팩터링하거나,
  주어진 데이터만으로 추론하는 작업이라면 검색 단계가 지연시간과 비용만 늘립니다
- **문서량이 작고 거의 바뀌지 않는 경우** — 문서 몇 개를 프롬프트에 그대로 넣어도 되는
  규모라면, Chunking·Indexing 파이프라인을 만드는 비용이 얻는 이득보다 클 수 있습니다
- **최신 API 응답이나 실시간 수치가 필요한 경우** — 재고 수량, 오늘 환율처럼 매 순간
  바뀌는 값은 벡터 검색 대상이 아니라 Tool Call로 시스템에 직접 물어보는 편이 정확합니다
- **정답이 문서가 아니라 규칙·계산에 있는 경우** — 세금 계산, 승인 로직처럼 결정론적
  규칙이 있는 문제는 검색보다 Rule/Policy 엔진이 맞습니다. RAG는 확률적으로 "그럴듯한"
  답을 만드는 구조라, 규칙이 명확한 판단에는 오히려 안 맞습니다

반대로 "회사 안에만 있는 지식을, 계속 바뀌는 상태로, 여러 사람이 자연어로 물어봐야 한다"는
조건이 겹치면 RAG가 맞는 선택일 가능성이 큽니다.

## 근거로 쓴 경험

건설사 A와 내부 기준을 자연어로 질의하는 챗봇을 기획하면서, 단순 LLM 답변이 아니라
내부 문서를 검색해 답하는 RAG 형태가 필요하다고 판단했습니다. 기업 환경이라 검색
품질뿐 아니라 **권한과 감사로그**까지 함께 설계 범위로 정의했습니다.

## 자주 나오는 질문

**Vector Search만 쓰나요?**
아닙니다. Vector Search는 "의미가 비슷한 것"을 잘 찾지만, 정확한 코드값이나 고유명사처럼
"글자가 일치하는 것"은 Keyword Search가 더 잘 찾습니다. 실무에서는 둘을 같이 씁니다.

**평가는 어떻게 하나요?**
검색(근거를 찾았는가), 판단(맞는 근거를 골랐는가), 생성(근거로 답을 제대로 썼는가) —
이 셋을 나눠서 봐야 합니다. 뭉뚱그려 "답변이 그럴듯한가"만 보면 어디가 문제인지 알 수 없습니다.

**문서가 업데이트되면요?**
원본이 바뀌면 해당 Chunk만 다시 색인하는 갱신 감지가 있어야 합니다. 없으면 정확도가
시간이 갈수록 조용히 떨어집니다.

**권한이 다르면요?**
검색 결과를 나중에 걸러내는 방식으로는 부족합니다. Chunk 단위로 접근 권한을 붙여
색인 단계에서부터 반영해야, 볼 수 없는 사람에게 안 보이는 것이 보장됩니다.

## 체크리스트 — RAG 여부를 판단하기 전에

| 확인 항목 | 예/아니오 |
|---|---|
| 외부 문서를 참조해야 답할 수 있는 질문인가 |  |
| 그 문서가 계속 바뀌는가 |  |
| 여러 사람이 자연어로 질문할 것인가 |  |
| 문서량이 프롬프트에 다 넣기엔 많은가 |  |
| 정답이 규칙이 아니라 문서 안에 있는가 |  |

다섯 개 중 대부분이 "예"라면 RAG를 검토할 시점입니다. "아니오"가 많다면
더 단순한 방법(직접 프롬프트, Tool Call, Rule 엔진)부터 확인하는 편이 낫습니다.

## 정리

RAG는 LLM의 기억을 늘리는 기술이 아니라, **모델이 답하기 전에 검색을 한 번 거치게
만드는 구조**입니다. 그리고 그 구조의 성패는 모델이 아니라 검색 품질, 그중에서도 Chunking과
권한 설계에서 갈립니다.

정의를 넘어 실제로 무엇부터 만들고, 기업 환경에서 어디가 터지는지는
[RAG 구축 절차와 실패 지점](/ax/foundation/rag-build-process-and-failures/)에서 이어집니다.
RAG가 그 앞단에서 다루는 데이터 계층과 어떻게 연결되는지는
[데이터 아키텍처 정리 — Lake·Warehouse·Mart와 RAG 구축](/ax/foundation/data-architecture-for-agents/)을 참고하세요.
