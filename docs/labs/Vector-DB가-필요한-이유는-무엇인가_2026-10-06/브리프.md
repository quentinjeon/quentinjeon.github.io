## 한 문장 정의

임베딩이 수십만 개 쌓이면 질문 벡터 하나를 전체와 일일이 비교할 수 없다.
Vector DB 는 **유사한 벡터를 빠르게 찾기 위한 인덱스**다.

보통 이런 일을 맡는다.

```text
Vector 저장 · ANN 검색 · Metadata · Filter · Index 관리
```

## 꼭 별도 제품이어야 하나

아니다. `PostgreSQL + pgvector` 같은 확장으로도 된다.

| 상황 | 선택 |
|---|---|
| 문서 수천~수만 건, 기존 RDB 가 있음 | RDB 의 vector 확장으로 충분 |
| 수십만~수백만, 검색이 핵심 기능 | 전용 Vector DB 검토 |
| 필터 조건이 복잡 (권한·부서·기간) | 메타데이터 필터 성능을 먼저 본다 |

## 실패 지점

- **규모를 모른 채 전용 제품부터 도입한다.** 운영 부담만 늘고 이점이 없다
- 권한 필터를 검색 후에 걸어 성능과 보안이 동시에 무너진다
- 인덱스 재구축 비용을 계산하지 않아 갱신을 포기하게 된다

## 면접용 정리

> Vector DB 가 RAG 의 본질은 아닙니다. 핵심은 **의미 기반 Retrieval** 이고,
> 데이터 규모와 기존 아키텍처에 따라 일반 DB 의 vector 확장을 쓸 수도, 전용 제품을 쓸 수도 있습니다.

특정 제품 경험을 억지로 주장할 필요가 없다.
