RAG를 검색하면 거의 항상 "벡터 DB 도입"이 첫 단계로 나옵니다.
그런데 실제로 문서가 수천 건 수준이라면, 전용 벡터 DB 없이도 RAG가 돌아갑니다.
이 글은 **언제 필요 없는지**부터 짚고, 필요해지는 시점을 규모와 운영 조건으로 정리합니다.

## 한 문장 정의

임베딩이 수십만 개 쌓이면 질문 벡터 하나를 전체와 일일이 비교할 수 없습니다.
**벡터 데이터베이스(Vector DB)는 유사한 벡터를 빠르게 찾기 위한 인덱스**입니다.

보통 이런 일을 맡습니다.

```text
Vector 저장 · ANN 검색 · Metadata · Filter · Index 관리
```

핵심은 ANN(Approximate Nearest Neighbor)입니다. 전체를 다 비교하는 대신,
정확도를 약간 포기하고 "거의 가장 가까운" 벡터를 훨씬 빠르게 찾아줍니다.
문서 수가 적을 때는 이 트레이드오프가 아직 필요하지 않습니다.

## Vector DB가 왜 필요한가요

가장 단순한 검색은 브루트포스입니다. 질문 벡터 하나를 저장된 벡터 전체와
코사인 유사도로 비교해, 가장 가까운 순으로 줄을 세웁니다. 벡터가 수백~수천
개면 이 방식으로도 체감상 즉시 응답합니다. 특별한 인덱스가 필요 없습니다.

문제는 전체 비교 비용이 벡터 개수에 비례해서 늘어난다는 점입니다. 개수가
수십만, 수백만으로 늘면 질문 하나당 비교 연산이 그만큼 늘어 응답이 느려집니다.
이때 HNSW, IVF 같은 ANN 인덱스를 쓰면, 전체를 다 보지 않고도 "거의 가장
가까운" 결과를 훨씬 빠르게 찾습니다. **Vector DB가 필요해지는 이유는 결국
이 인덱스 구조를 직접 관리하지 않기 위해서**입니다. 저장·인덱싱·재구축을
제품이 대신 해 줍니다.

즉 "RAG를 하려면 Vector DB가 있어야 한다"가 아니라, "벡터가 많아져서
브루트포스가 느려지는 시점에 인덱스가 필요하다"가 맞는 순서입니다.

## 꼭 별도 제품이어야 하나

아니요. `PostgreSQL + pgvector` 같은 확장으로도 됩니다.
전용 벡터 DB는 ANN 검색 하나를 더 빠르고 더 많은 규모로 하기 위한 선택지일 뿐,
RAG가 성립하는 데 필수 전제는 아닙니다.

| 상황 | 선택 |
|---|---|
| 문서 수천~수만 건, 기존 RDB 가 있음 | RDB 의 vector 확장으로 충분 |
| 수십만~수백만, 검색이 핵심 기능 | 전용 Vector DB 검토 |
| 필터 조건이 복잡 (권한·부서·기간) | 메타데이터 필터 성능을 먼저 본다 |

이미 운영 중인 PostgreSQL이 있다면, 거기에 pgvector 확장을 얹는 쪽이
새 인프라를 하나 더 들여오는 것보다 운영 부담이 작습니다.
백업·모니터링·권한 체계를 이미 갖춘 시스템에 기능을 하나 추가하는 것과,
낯선 제품을 새로 운영하는 것은 비용이 다릅니다.

## 규모 기준은 어떻게 잡나요

"문서가 많다"는 느낌으로 판단하지 않습니다. 기준은 두 가지입니다.

- **전체 벡터 개수** — 수만 건 이하라면 RDB의 vector 확장이 내는 지연으로도
  서비스 요구사항을 맞추는 경우가 많습니다. 검색이 느려지는 시점은 데이터가
  아니라 쿼리 패턴(동시 요청 수, 필터 복잡도)에서 먼저 옵니다.
- **검색이 제품의 핵심 기능인가** — 사내 문서 검색 보조 기능이라면 지연에
  여유가 있습니다. 검색 결과 자체가 상품이라면(추천, 유사 사례 검색) 전용
  제품의 최적화가 체감 차이를 만듭니다.

규모를 모른 채 전용 제품부터 들여오는 쪽이 오히려 흔한 실수입니다.
운영 부담만 늘고, 쓰지 않는 기능(샤딩, 분산 인덱스)에 대한 복잡도를 떠안게 됩니다.
도입을 먼저 정하고 규모를 나중에 맞추는 순서가 아니라, 지금 벡터 개수와
증가 속도를 먼저 세어 보고 그 다음에 제품을 고르는 순서가 맞습니다.
마이그레이션은 나중에도 할 수 있습니다. 처음부터 가장 큰 규모를 가정해
설계를 무겁게 가져갈 필요는 없습니다.

## 권한 필터는 어디서 거나요

여기서 많이 틀립니다. **검색 결과를 받은 다음에 권한으로 걸러내는 방식은 부족합니다.**
벡터 검색은 이미 벡터 공간에서 "비슷한 것"을 다 찾아 끝난 상태이고,
그 뒤에 결과만 지우는 방식으로는 "몇 건이 나왔다"는 정보 자체를 막지 못합니다.

조각(chunk) 단위로 접근 주체를 메타데이터에 붙여, **색인 시점에 필터링**하는
구조여야 합니다. 이 부분은 벡터 DB를 고를 때 "메타데이터 필터 성능"을
먼저 확인해야 하는 이유이기도 합니다. 필터 조건이 복잡할수록(권한·부서·기간이
동시에 걸리는 경우) 전용 제품의 필터 인덱스 설계가 차이를 만듭니다.

이 권한 문제와 RAG 파이프라인 전체의 실패 지점은
[RAG 구축 절차 — 파이프라인은 6단계, 실패는 4곳에서 난다](/ax/foundation/rag-build-process-and-failures/)
에서 더 자세히 다뤘습니다.

## 인덱스 갱신은 어떻게 하나요

원본 문서는 계속 바뀝니다. 인덱스 갱신 비용을 미리 계산하지 않으면,
결국 "다음에 전체 재색인할 때 하자"로 미뤄지다가 갱신 자체를 포기하게 됩니다.

전체 재색인은 데이터가 커질수록 비용이 커집니다. 그래서 바뀐 조각만
다시 임베딩하고 인덱스에 반영하는 **증분 갱신** 경로가 있는지를
도입 전에 확인해야 합니다. 이 경로가 없으면 시간이 지날수록 검색 결과가
조용히 낡아갑니다. 사고가 나기 전까지는 아무도 알아채지 못합니다.

## 도입 전 체크리스트

- [ ] 전체 벡터 개수가 수만 건을 넘는가, 아니면 수십만~수백만 단위인가
- [ ] 검색 결과 자체가 제품의 핵심 기능인가, 보조 기능인가
- [ ] 권한·부서·기간 같은 메타데이터 필터가 복잡한가
- [ ] 필터링을 색인 시점에 거는가, 검색 후에 거는가
- [ ] 원본이 바뀌었을 때 조각 단위 증분 갱신이 되는가, 전체 재색인만 되는가
- [ ] 이미 운영 중인 RDB가 있어 pgvector 확장으로 충분한지 먼저 검토했는가

데이터가 어느 계층(Lake·Warehouse·Mart)에 있고 어떻게 Agent가 읽을 상태로
이어지는지는 [데이터 아키텍처 개념정리 — Lake·Warehouse·Mart에서 Agent Action까지](/ax/foundation/data-architecture-for-agents/)
에서 다뤘습니다. 벡터 DB는 그 흐름 중 검색 가능한 상태를 만드는 한 조각입니다.

## 이렇게 정리합니다

> Vector DB가 RAG의 본질은 아닙니다. 핵심은 **의미 기반 Retrieval**이고,
> 데이터 규모와 기존 아키텍처에 따라 일반 DB의 vector 확장을 쓸 수도,
> 전용 제품을 쓸 수도 있습니다.

특정 제품을 추천하는 글이 아닙니다. 규모, 필터, 갱신 비용이라는 세 기준으로
먼저 판단하고, 그 다음에 제품을 고르는 순서를 권합니다.
