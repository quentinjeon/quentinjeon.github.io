## 한 문장 정의

질문 20개를 대충 돌려보는 건 평가가 아니다.
**대표적인 실제 업무를 표집해 평가셋을 만들고, 실패를 종류별로 분리해 측정하는 것**이 평가다.

## 평가셋 구성

```text
FAQ · 제품 문의 · 비교 · 가격 · 구매처
불명확 질문 · Out-of-domain · 악의적 질문
```

**답하지 않아야 하는 사례를 반드시 넣는다.** 없으면 아무 말이나 하는 시스템이 좋은 점수를 받는다.

## 평가 방법 세 가지

| 방법 | 쓰임 | 주의 |
|---|---|---|
| 정량 평가 | Accuracy·Precision·Recall·F1 | 과제에 맞는 지표인지 |
| LLM-as-a-Judge | 빠른 반복 | 편향이 있어 사람 평가와 대조 필요 |
| Human Evaluation | 정확성·근거성·유용성·완결성 | 비용이 크므로 표본 설계가 중요 |

## RAG 라면 반드시 분리한다

```text
Retrieval Evaluation   근거 문서를 찾았는가
        +
Generation Evaluation  찾은 근거로 제대로 답했는가
```

검색이 틀린 건지, 검색은 맞았는데 생성이 틀린 건지를 나눠야 **고칠 곳을 안다.**

## 실패 지점

- 테스트 정답을 보며 프롬프트·임계값을 조정한다 → 평가셋이 점수 생산 도구가 된다
- Train·Dev·Test 를 대화가 아니라 문장 단위로 나눠 정보가 샌다
- 점수만 보고하고 **어떤 오류가 줄었는지** 말하지 못한다

## 좋은 연구 설계 흐름

```text
Human Gold → Baseline → Failure Analysis → Method
```
