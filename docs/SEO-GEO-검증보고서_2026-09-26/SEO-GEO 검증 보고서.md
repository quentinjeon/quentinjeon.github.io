## 한 줄 결론

콘텐츠는 이미 상위권 경쟁이 가능한 수준인데, **기계가 읽는 층이 거의 비어 있습니다.**
측정(GA4)·구조화 데이터·검색엔진 등록이 셋 다 0이고, 본문 이미지가 글당 평균 4MB입니다.
글을 더 쓰기 전에 이 네 가지를 먼저 메우는 편이 효율이 높습니다.

## 심각도 순 발견 사항

### P0-1. GA4가 설치되어 있지 않습니다

홈·목록·글 상세 어디에도 `gtag` / `googletagmanager` / GTM 스크립트가 없습니다.
지금은 **누가 들어와서 무엇을 읽고 나갔는지 아무 기록이 남지 않습니다.**
뉴스레터 구독 전환율도 측정할 수 없습니다.

테마는 이미 GA4를 지원합니다. `_includes/analytics-providers/google-gtag.html` 이 존재하고
`_includes/scripts.html` 에서 호출됩니다. **설정 세 줄만 채우면 됩니다.**

```yaml
analytics:
  provider               : "google-gtag"
  google:
    tracking_id          : "G-XXXXXXXXXX"
    anonymize_ip         : true
```

> 주의: 테마의 `analytics.html` 은 `jekyll.environment == 'production'` 조건이 붙어 있습니다.
> GitHub Pages 빌드는 자동으로 production 이라 정상 동작하지만, 로컬 `jekyll serve` 에서는 안 찍힙니다.
> 로컬에서 안 보인다고 설정이 틀린 게 아닙니다.

### P0-2. 글 페이지에 구조화 데이터가 전혀 없습니다

42개 중 **41개**에 JSON-LD가 없습니다. 홈에만 1개 있는데 그 내용도 이렇습니다.

```json
{ "@type": "Person", "name": "Quentin Jeon", "url": "https://quentinjeon.github.io/" }
```

- `sameAs` 가 없어 GitHub·YouTube·Threads 계정과 **연결되지 않습니다.**
- 글에 `Article` / `BlogPosting` 스키마가 없어 **작성자·발행일·주제가 기계에게 전달되지 않습니다.**
- 테마의 `_includes/schema.html` 은 홈에서만 호출되고, 그나마 Person 최소 필드만 찍습니다.

검색 결과의 작성자·날짜 표시, 그리고 AI 검색엔진이 "누가 쓴 글인가"를 판단하는 데 직접 쓰이는 층입니다.

### P0-3. 본문 이미지가 너무 무겁습니다

| 글 | 본문 이미지 | 합계 | 최대 한 장 |
|---|---:|---:|---:|
| data-architecture-for-agents | 14장 | **9.0MB** | 725KB |
| vibe-agent-workspace | 6장 | **7.7MB** | **1,338KB** |
| pmp-10-knowledge-areas | 10장 | 6.2MB | 655KB |
| energy-ax-integrated-operations | 8장 | 4.6MB | 804KB |
| vibe-agent-workspace-part2 | 6장 | 4.0MB | 730KB |

**평균 4.2MB.** 여기에 더해

- `loading="lazy"` 가 **한 장도** 없습니다 → 화면에 안 보이는 이미지까지 전부 즉시 내려받습니다
- `width` / `height` 속성이 **한 장도** 없습니다 → 레이아웃이 밀립니다 (CLS 악화)
- WebP 파일 **0개**, 800KB 초과 원본 **11개** (최대 2.6MB)

모바일 LTE에서 글 하나 여는 데 몇 초가 걸립니다. Core Web Vitals는 순위 신호이고,
느린 페이지는 AI 크롤러에게도 불리합니다.

### P1-1. 검색엔진에 한 곳도 등록되어 있지 않습니다

`_config.yml` 의 인증값이 전부 공란입니다.

```
google_site_verification :
bing_site_verification   :
naver_site_verification  :
yandex_site_verification :
```

독자가 한국어권이면 **네이버 서치어드바이저 등록이 구글만큼 중요합니다.**
다음(카카오)도 별도 등록이 필요합니다. 지금은 사이트맵을 만들어 두고 아무에게도 알리지 않은 상태입니다.

### P1-2. 이름 표기가 세 가지로 갈립니다

| 표기 | 쓰이는 곳 |
|---|---|
| 전용섭 Yongsub Jeon | 사이트 제목, 작성자, about 페이지(13회) |
| **Quentin Jeon** | `_config.yml` 의 `name` → **JSON-LD 의 Person.name** |
| quentinjeon | 도메인, GitHub 계정 |

AI 검색엔진은 여러 출처를 묶어 "이 사람이 누구인가"라는 엔티티를 만듭니다.
대표 표기를 하나로 고정하고 나머지를 `alternateName` 과 `sameAs` 로 묶어줘야 하나의 인물로 인식됩니다.

### P1-3. 공유 카드가 비어 있습니다

- `og:image` 없음: **22개 페이지** (홈, /ax/, /labs/, /work/ 등 목록 페이지 전부 + 일부 프로젝트)
- `twitter:card` : **42개 전부 없음** — `site.twitter.username` 이 비어 있어 테마가 출력을 건너뜁니다
- `og_image` 기본값 공란 → 이미지가 없는 페이지는 대체 이미지조차 없음

Threads·X·카카오톡에 링크를 붙이면 그림 없는 맨 링크로 나갑니다. 유입에 직접 영향이 있습니다.

### P2-1. llms.txt 가 없습니다 (GEO)

`/llms.txt` → **404**. AI 검색엔진·에이전트에게 "이 사이트의 핵심 문서가 무엇인지"를
알려주는 관례적 파일입니다. 아직 표준은 아니지만 **비용이 거의 0이고 손해가 없습니다.**

robots.txt 는 정상이고 AI 크롤러를 막고 있지 않습니다(`Sitemap:` 한 줄만 존재).
GEO 관점에서는 **차단하지 않은 현재 상태가 맞습니다.**

### P2-2. H1이 두 개인 페이지가 3곳

| 페이지 | 테마가 찍는 H1 | 본문이 또 찍는 H1 |
|---|---|---|
| /foodtech/first/ | FOODTECH IN ROBOTICS! | `Welcome` |
| /work/ | 프로젝트 | `도구 · 실험` |
| /robotics/아두이노-Serial통신… | 아두이노 시리얼 통신으로 서보모터 각도 조절하기 | `아두이노 시리얼 통신을 통해, 서보모터 각도 조절하기` (거의 같은 문장) |

본문 마크다운의 `#` 이 테마의 페이지 제목 H1과 겹칩니다. `##` 로 내리면 끝납니다.

### P2-3. 제목·설명 길이

- **제목 60자 초과 9개** → 검색 결과에서 뒤가 잘립니다. 가장 긴 것 77자
- **설명 70자 미만 25개** → 대부분 목록 페이지. 클릭을 유도할 문장이 부족합니다
- 설명 160자 초과는 0개 (양호)

### P2-4. Part 3 글에 이미지가 하나도 없습니다

`/ax/foundation/vibe-agent-workspace-part3/` 본문에 `<img>` **0개**, 8,087자 전부 텍스트입니다.
이전 작업에서 이미지 프롬프트(`docs/…_2026-08-23/IMAGE-PROMPTS.md`)만 만들고
실제 이미지가 채워지지 않은 채 배포됐습니다. 1·2편과 품질이 눈에 띄게 차이 납니다.

### P3. 그 밖에

- **본문 외부 링크 0개** — 근거로 인용한 외부 출처가 없습니다. GEO에서 인용은 신뢰 신호입니다
- **/tags/ 페이지 182KB** — 다른 페이지 평균의 4배. 태그가 늘수록 더 무거워집니다
- 목록 썸네일 `alt=""` 99개 — 제목 텍스트가 같은 링크 안에 있어 **접근성상 틀린 것은 아닙니다.** 우선순위 낮음
- 사이트맵 42개 중 `lastmod` 가 붙은 것은 18개 (글에만 날짜가 있음)

## GEO(생성형 검색 최적화) 관점 정리

일반 SEO와 겹치지 않는 부분만 따로 봤습니다.

**이미 잘 되어 있는 것**

- 글이 깁니다(AX 글 10편 평균 **9,500자**, 최소 6,599자) — AI가 인용할 만한 밀도가 있습니다
- h2 18개처럼 **소제목이 촘촘**합니다. 답변에 필요한 구간만 뽑아 쓰기 좋습니다
- 실제 실행 결과·수치가 본문에 들어 있습니다(이벤트 31건, 312줄 같은 구체값)
- **고유 개념의 정의문이 실제로 있습니다.** 대표 글 본문 **11% 지점**에
  "한 문장으로 정의하면 …" 형태로 명시되어 있습니다. 인용되기 좋은 형태입니다
- AI 크롤러를 차단하지 않고 있습니다

**비어 있는 것**

- **저자 신뢰 신호**: Person 스키마에 `sameAs`·`jobTitle`·`knowsAbout` 이 없습니다.
  AI가 "이 사람이 이 주제를 말할 자격이 있나"를 판단할 근거가 사이트 안에 없습니다
- **맨 앞의 요약 블록**: 글이 "처음 가설은 단순했다" 같은 서사로 시작합니다.
  정의는 11% 지점에 잘 쓰여 있지만, 그 앞 1,100자를 먼저 읽어야 나옵니다.
  **이미 쓰신 그 정의 문장을 글 맨 위로 한 번 더 올리는 것만으로 충분합니다.** 새로 쓸 필요가 없습니다
- **정의의 마크업**: 정의문이 일반 문단으로만 존재합니다.
  `DefinedTerm` / `FAQPage` 스키마나 최소한 별도 인용 블록으로 감싸면 기계가 집어내기 쉬워집니다
- **인용 가능한 외부 근거**: 본문 외부 링크 0개

> 솔직히 말씀드리면 GEO는 아직 검증된 방법론이 아닙니다.
> 위 네 가지는 "AI 검색에 잘 걸린다"가 증명된 기법이 아니라,
> **일반 SEO·접근성·문서 품질 관점에서도 어차피 이득인 것들**만 골랐습니다.
> 효과가 불확실한 GEO 전용 기법은 넣지 않았습니다.

## 설치 후 무엇을 볼 것인가

GA4를 붙이고 2주쯤 지나면 이 네 가지가 판단 근거가 됩니다.

1. **유입 경로 비중** — 검색 / 직접 / 소셜. 검색이 20% 미만이면 색인 문제
2. **글별 체류시간** — 8,000자 글에서 1분 미만이면 도입부에서 이탈
3. **뉴스레터 전환율** — 글 조회 대비 구독. 폼 두 곳(하단·팝업)을 나눠 보려면 이벤트를 따로 심어야 합니다
4. **네이버 vs 구글 비중** — 독자층이 어디에 있는지가 다음 글 주제 선정에 영향

## 이번 점검에서 확인하지 못한 것

정직하게 적어둡니다.

- **실제 순위와 노출량** — Search Console 미등록이라 조회 불가
- **Core Web Vitals 실측값** — 실제 사용자 데이터(CrUX)가 쌓이려면 트래픽이 필요합니다.
  위 이미지 수치는 파일 크기 실측이지, LCP·CLS 측정값이 아닙니다
- **백링크** — 외부 도구 없이 확인 불가
- **경쟁 키워드 난이도** — 별도 도구 필요
