`Spring Boot 3.4 · Kotlin · Next.js 16 · MySQL · Ollama` · [저장소](https://github.com/quentinjeon/telenews)

가장 오래 붙잡고 있는 시스템이고, **가장 많이 문제 정의가 바뀐** 시스템입니다.
기능 목록보다 그 변화를 남기는 게 나을 것 같아 이렇게 씁니다.

---

## 시작은 틀린 질문이었다

처음 세운 질문은 이거였습니다.

> "투자 정보가 뉴스·공시·차트로 흩어져 있으니, 한곳에 모으면 되지 않을까?"

RSS 19개사, 텔레그램, DART 공시, Yahoo Finance를 붙였습니다. 수집은 잘 됐습니다.
그리고 **모아놓으니 더 안 읽혔습니다.**

당연한 결과였습니다. 하루에 수백 건이 들어오는데, 그중 같은 사건을 다룬 기사가 열 건씩 섞여 있습니다.
사람이 하던 일은 "찾기"가 아니라 **"같은 걸 걸러내고 중요한 걸 고르기"**였는데,
저는 찾기를 자동화하고 나머지를 그대로 사람에게 남겨둔 셈이었습니다.

수집은 문제의 10%였습니다.

---

## 결정 1 — 뉴스·공시·리서치를 한 테이블에 넣는다

처음엔 `news`, `disclosure`, `research` 테이블을 따로 두려고 했습니다. 성격이 다르니까요.

그런데 사용자가 던지는 질문은 테이블 경계를 따르지 않습니다.
"삼성전자에 오늘 무슨 일 있었어?"라는 질문에 뉴스만 답하거나 공시만 답하는 건 의미가 없습니다.

그래서 단일 `articles` 테이블에 `content_type`(NEWS / DISCLOSURE / RESEARCH)으로 통합했습니다.

**대가가 있었습니다.** 공시에만 있는 필드(접수번호·보고서 종류)와 뉴스에만 있는 필드(기자·썸네일)가
한 테이블에서 서로 `NULL`로 남습니다. 정규화 관점에서는 지는 설계입니다.

그래도 이쪽을 택한 이유는, **조인을 줄이는 것보다 "한 사건"이라는 개념을 지키는 게 중요하다**고 봤기 때문입니다.
클러스터링을 붙이는 순간 이 결정이 값을 했습니다. 공시와 뉴스가 같은 클러스터에 들어갈 수 있게 됐으니까요.

---

## 결정 2 — 외부 API를 쓰지 않는다

요약·분류·임베딩을 전부 로컬 Ollama(`qwen2.5:3b` + `bge-m3`)로 돌립니다. 외부 API 키가 없습니다.

성능만 보면 지는 선택입니다. 단건 요약에 8~36초가 걸립니다. GPT-4o를 부르면 훨씬 빠르고 정확합니다.

그럼에도 이렇게 한 이유는 **실험 횟수** 때문입니다.

종량 과금이면 "전체 기사 재분류"를 누르기 전에 매번 비용을 계산하게 됩니다.
그 망설임이 쌓이면 튜닝을 안 하게 됩니다. 로컬이면 밤새 열 번 돌려도 전기값뿐입니다.

느린 대신 **마음껏 틀릴 수 있는 환경**을 산 것입니다.
정확도가 중요한 지점에서는 나중에 외부 모델로 갈아끼울 수 있게 어댑터를 분리해 뒀습니다.

---

## 결정 3 — LLM을 마지막에 부른다

분류를 처음엔 LLM에 통째로 맡겼습니다. 느리고, 비싸고, 무엇보다 **왜 그렇게 분류했는지 알 수 없었습니다.**

그래서 4단 결정 트리로 바꿨습니다.

```
1. 키워드 매칭        기존 규칙 점수
2. 임베딩 코사인       bge-m3 vs 카테고리 anchor
3. 소스 가중치        소스별 카테고리 분포
4. AI 백업           ← 위 셋의 신뢰도가 낮을 때만
```

이건 다른 프로젝트에서도 반복해서 내리는 판단입니다.
[HACCP FLOW](/work/haccp-flow/)에서도 LLM은 후보만 만들고 판정은 규칙엔진이 합니다.
**LLM을 빼는 게 아니라, LLM을 마지막에 두는 것**입니다.

### 그런데 이건 아직 잘 안 됩니다

정직하게 적어야 할 부분입니다. 아래는 실제 화면입니다.

[![투자 정보 피드 — 트렌딩 클러스터](/assets/images/work/telenews-01-feed.jpg)](/assets/images/work/telenews-01-feed.jpg)
*지금 뜨는 이슈 — 클러스터링은 작동하지만 분류는 틀린다. 클릭하면 원본 크기.*

**작동하는 것**: 클러스터링은 실제로 됩니다. 첫 카드는 `17건 · 9개 소스`,
두 번째는 `11건 · 6개 소스`로 여러 매체가 같은 사건으로 묶여 있습니다.
중복 제거라는 원래 목표는 달성했습니다.

**작동하지 않는 것**: 분류가 눈에 띄게 틀립니다.

| 기사 | 분류 결과 | 문제 |
|---|---|---|
| 이란 관련 선박 호르무즈 통과 | `IT/기술` | 해외·정치여야 함 |
| 낮 최고 27도 초여름 날씨 | `IT/기술` | 날씨 기사 |
| 완도 냉동창고 화재 | `IT/기술` | 사회 |
| 대전 오월드 탈출 늑대 발견 | `경제` | 사회 |

`IT/기술`로 쏠리는 패턴이 보입니다. 4단 트리 중 어느 단계가 원인인지는 아직 분리해 보지 못했습니다.
카테고리 anchor 텍스트가 너무 일반적이라 임베딩 유사도가 뭉개졌을 가능성을 먼저 의심하고 있습니다.

그리고 더 근본적인 문제가 하나 더 보입니다.
**"투자 정보 피드"인데 트렌딩 상위가 날씨·늑대·트럼프 이미지 논란입니다.**
트렌딩 점수에 "투자 관련성"이라는 축이 아예 없기 때문입니다.
많이 보도된 것과 투자 판단에 필요한 것은 다른데, 저는 전자만 측정하고 있었습니다.

## 결정 4 — "무엇이 중요한가"를 코드에서 꺼낸다

트렌딩 점수 공식을 처음엔 코드 상수로 뒀습니다. 그런데 이 값은 **정답이 없고 계속 바뀝니다.**
장중과 장 마감 후가 다르고, 공시 시즌과 아닌 때가 다릅니다.

바뀌는 값을 코드에 두면 그때마다 배포해야 하고, 배포가 필요하면 결국 안 바꾸게 됩니다.
그래서 가중치를 관리자 화면으로 꺼냈습니다.

[![트렌딩 랭킹 튜닝](/assets/images/work/telenews-02-ranking.jpg)](/assets/images/work/telenews-02-ranking.jpg)
*가중치를 움직이면 우측 top-12가 즉시 재정렬된다. 클릭하면 원본 크기.*

여기서 신경 쓴 건 슬라이더가 아니라 **그 주변의 안전장치**입니다.

- **`저장 전까지는 서비스 사용자에게 영향이 없습니다`** — 미리보기와 발행을 분리했습니다.
  [청라 Data Hub](/work/)에서 `Upload ≠ Publish`로 풀었던 것과 같은 문제입니다.
- **`가중치 합 1.00 / 1.00`** — 합이 1에서 멀어지면 점수 스케일이 왜곡된다고 화면이 먼저 경고합니다.
- **`새 알고리즘 활성화` 토글** — 끄면 기존 `trending_score` 정렬로 폴백합니다. 되돌릴 길을 먼저 만들어 둔 것입니다.
- **`MMR λ 0.700`** — 관련성만 보면 상위가 비슷한 기사로 도배됩니다. 다양성을 섞는 값을 따로 뺐습니다.

프롬프트도 같은 이유로 배포에서 분리했습니다.
관리자 UI에서 편집하고, 드라이런으로 검증한 뒤 활성화합니다. 버전은 불변으로 쌓이고 롤백됩니다.

## 그리고 문제 정의가 한 번 더 바뀌었다

여기까지 만들고 나서 스스로에게 물었습니다.

> "이슈를 잘 묶어서 보여주면, 사용자가 더 나은 판단을 하게 되나?"

아니라고 봤습니다. **정보를 더 잘 정리해 줘도 판단은 여전히 휘발됩니다.**
왜 그때 샀는지, 무슨 근거였는지가 남지 않으면 다음 판단이 나아지지 않습니다.

그래서 `/me` 영역을 만들기 시작했습니다. 관심종목 브리프, 포트폴리오,
그리고 핵심인 **의사결정 이력** — 매수·매도·보류를 사유와 함께 기록하고 결과를 나중에 대조하는 것.

읽는 시스템에서 **판단을 기록하는 시스템**으로의 이동입니다.

[![의사결정 이력](/assets/images/work/telenews-03-decisions.jpg)](/assets/images/work/telenews-03-decisions.jpg)
*의사결정 이력 — 화면은 있고 내용은 없다. 클릭하면 원본 크기.*

**그리고 이건 아직 화면만 있습니다.** 위 캡처가 현재 상태입니다.
`의사결정 이력이 없습니다`. 사이드바에는 `STAGE 4 정리 예정`,
일일 다이제스트·가설 트래커·다이어리에는 `SOON` 배지가 붙어 있습니다.

저장소 README에는 이 기능들이 완성된 것처럼 적혀 있는데, 실제로는 골격만 선공개한 상태입니다.
포트폴리오에 올리면서 그대로 옮기는 건 맞지 않다고 생각해 여기 바로잡습니다.

| 랭킹 가중치 운영자 튜닝 | ✅ 미리보기·폴백·합계 검증 포함 |
| 프롬프트 무배포 편집 | ✅ 버전 불변 + 롤백 |
| **카테고리 분류 정확도** | ⚠️ **눈에 띄게 틀림. 원인 미분리** |
| **트렌딩의 투자 관련성** | ⚠️ **측정 축 자체가 없음** |
| **의사결정 이력 / 다이제스트 / 가설 트래커** | 🔧 **UI 골격만. 데이터 없음** |

규모만 적으면 이렇습니다 — Kotlin/Spring Boot 백엔드에 Clean Architecture 4계층,
MySQL 40여 테이블, 21개 cron job, Next.js 16 프론트, 화면 35장.
다만 **규모는 이 시스템에서 가장 덜 중요한 숫자**입니다.

## 남은 질문

1. **분류가 왜 `IT/기술`로 쏠리는가.** anchor 텍스트, 소스 가중치, 임계값 중 어디가 원인인지 분리해야 합니다.
   4단을 한꺼번에 넣은 탓에 실패 원인도 4단으로 섞여 있습니다 — 단계별 기여도를 측정할 수 있게 만들어 두지 않은 게 설계 실수입니다.
2. **"투자 관련성"을 어떻게 점수화할 것인가.** 종목 임팩트 가중치가 있긴 하지만
   종목 태그가 붙은 기사에만 작동합니다. 태그가 없는 거시 기사는 잡히지 않습니다.
3. **의사결정 이력에 무엇을 최소로 담아야 사람이 실제로 쓰는가.** 입력이 무거우면 아무도 안 씁니다.
   지금 설계는 아직 무겁습니다.

세 번째가 제일 어렵습니다. 앞의 둘은 정확도 문제라 측정하면 개선되지만,
세 번째는 **사람이 자기 판단을 기록할 마음이 드는가**의 문제라 기술로 풀리지 않습니다.
