> **1~5단계 · 문제 정의와 기초 수학**
> 이 구간의 질문: **행동의 '수준'을 왜 별도로 선택해야 하는가**

> **읽기 전 주의**
> 기반 문서는 문제 정의·수학적 모델·아키텍처·벤치마크와 실험 계획을 제안하는 **연구 설계 초안**입니다.
> 실험 결과가 제시된 상태가 아니므로, 제안 방식이 기존 방식보다 낫다는 내용은 **아직 검증해야 할 가설**로 읽어야 합니다.
{: .notice--warning}

현대의 LLM 에이전트는 답변만 생성하지 않는다. API를 호출하고, 여러 작업을 묶은 Skill을 실행하며, 다른 Agent에게 하위 목표를 위임하고, 사람에게 질문하거나 승인을 요청한다. 실패하면 재계획·재시도·롤백·종료 같은 Control 행동도 수행한다.

이때 핵심 문제는 단순히 **“다음에 어떤 API를 호출할 것인가?”**가 아니다. 먼저 다음 두 질문을 분리해야 한다.

1. 지금 상태에서 **어느 수준에서 행동해야 하는가?**
2. 선택한 수준 안에서 **어떤 구체 행동을 실행해야 하는가?**

이 글은 `At What Level Should an Agent Act?`의 문제 설정을 이해하기 위해 필요한 내용을 고등학교 수준의 집합·논리부터 컴퓨터 시스템, LLM Agent, MDP/SMDP, 권한·거버넌스, 벤치마크, MVP 구현까지 20단계로 정리한다.

> **연구 상태에 대한 주의**  
> 기반 문서는 문제 정의, 수학적 모델, 아키텍처, 벤치마크와 실험 계획을 제안하는 연구 설계 초안이다. 실제 실험 결과가 제시된 상태가 아니므로, 제안 방식이 기존 방식보다 우수하다는 내용은 아직 검증해야 할 가설로 다뤄야 한다.


## 이 글에서 다루는 범위

이 글은 단순 논문 요약이 아니라, 논문의 문제 설정을 이해하고 작은 시스템과 실험으로 옮기기 위한 학습·구현 로드맵이다. 전체 내용은 다음 네 구간으로 읽을 수 있다.

| 구간 | 단계 | 핵심 질문 | 최종 산출물 |
|---|---:|---|---|
| 문제 정의와 기초 수학 | 1~5 | 행동의 ‘수준’을 왜 별도로 선택해야 하는가 | 중심 논제, 행동 수준표, 전체 구조도 |
| 허용 판정과 시스템 기초 | 6~10 | 현재 상태에서 어떤 행동이 합법적·실행 가능한가 | F/A/C/V 진리표, 상태기계, Tool 계약 |
| Agent·강화학습·거버넌스 | 11~15 | 시간·조직·권한 경계를 어떻게 모델링할 것인가 | GH-SMDP 설명서, 권한표, 구조화 상태 |
| 구현과 검증 | 16~20 | 정책을 보존하며 구현하고 실험으로 검증할 수 있는가 | Typed Handoff, MVP, Benchmark, 연구 패키지 |

## 먼저 결론: 좋은 Agent는 무엇이 다른가

좋은 Agent는 가능한 모든 행동을 한꺼번에 보고 그럴듯한 하나를 고르는 시스템이 아니다. 다음 네 가지 책임을 분리한다.

```text
구조화된 상태
    ↓
Admissibility Compiler
현재 합법적이고 실행 가능한 후보를 계산
    ↓
Abstraction Router
허용 후보 중 적절한 수준과 행동을 선택
    ↓
Protected Runtime
실행 직전 최신 권한·정책·상태를 다시 강제
    ↓
Verifier
실제 효과와 사후조건을 검증하고 상태를 갱신
```

또한 Skill, Delegation, Human처럼 실행 경계가 바뀔 때는 `Goal`, `Constraint`, `Authority`, `Budget`, `Provenance`를 구조화된 계약으로 전달해야 한다. 그래야 하위 실행이 원래 목표를 벗어나거나, 필수 제약을 잊거나, 권한을 과도하게 확대하는 문제를 줄일 수 있다.

## 다섯 가지 행동 수준 한눈에 보기

| 행동 수준 | 쉬운 정의 | 대표 예 | 대표 위험 |
|---|---|---|---|
| Tool | 한 번의 제한된 환경 연산 | 주문 1건 조회 | 긴 업무에서 호출 수 폭증 |
| Skill | 여러 Tool과 판단을 묶은 절차 | 출하 가능성 일괄 점검 | 현재 상태와 절차의 불일치 |
| Delegation | 다른 판단 주체에 하위 목표 위임 | 품질 Agent에 인증서 검증 위임 | 목표·제약 손실, 권한 과다 |
| Human | 사람에게 정보·승인·예외 판단 요청 | 관리자 발송 승인 | 대기시간, 과도한 호출 |
| Control | 실행 흐름 자체를 변경 | 재계획·재시도·롤백·종료 | 무한 재시도, 과도한 차단 |

## 1단계. 논문의 중심 질문을 한 문장으로 고정하기

[![1단계. 논문의 중심 질문을 한 문장으로 고정하기](/assets/images/agent-level-step-01-core-question.png)](/assets/images/agent-level-step-01-core-question.png)
*1단계. 논문의 중심 질문을 한 문장으로 고정하기 — 클릭하면 원본 크기로 볼 수 있습니다.*

**핵심은 행동 선택을 두 층으로 분해하는 것이다.** 기존 Agent는 대개 “무엇을 할 것인가?”를 묻는다. 이 논문은 그보다 먼저 “Tool, Skill, Delegation, Human, Control 중 어느 수준에서 행동할 것인가?”를 묻는다.

예를 들어 지연 주문 250건을 처리해야 한다고 하자. 주문 1건만 확인하면 Tool이 적절하다. 정형화된 반복 점검이라면 Skill이 낫다. 손상된 인증서를 해석해야 한다면 전문 Agent 위임이 필요할 수 있다. 외부 메일 발송에 관리자 승인이 필요하다면 Human이 최적 행동이다.

**실습 산출물:** 논문 한 문장 요약, 기존 질문과 제안 질문의 비교표, ERP·제조업 예시 1개.  
**통과 기준:** “수준 선택”과 “수준 내부의 구체 행동 선택”을 서로 다른 문제로 설명할 수 있어야 한다.

## 2단계. 다섯 가지 행동 수준 구분하기

[![2단계. 다섯 가지 행동 수준 구분하기](/assets/images/agent-level-step-02-five-action-levels.png)](/assets/images/agent-level-step-02-five-action-levels.png)
*2단계. 다섯 가지 행동 수준 구분하기 — 클릭하면 원본 크기로 볼 수 있습니다.*

다섯 수준은 이름만 다른 API가 아니다. 실행 시간, 자율성, 책임 주체, 권한, 비용, 위험이 서로 다르다.

- **Tool**은 짧고 직접적이다.
- **Skill**은 여러 원시 행동을 시간적으로 압축한다.
- **Delegation**은 다른 의사결정 주체로 책임 경계를 옮긴다.
- **Human**은 정보·승인·예외 판단을 가진 조직 주체를 호출한다.
- **Control**은 비즈니스 상태보다 실행 흐름을 바꾼다.

**실습 산출물:** 실제 업무 행동 20개를 다섯 수준으로 분류한 표.  
**통과 기준:** 주문 조회에 전문 Agent를 부르는 것이 왜 과도한지, 반대로 전문 판단 업무를 Tool 반복으로 처리하는 것이 왜 부족한지 설명할 수 있어야 한다.

## 3단계. 전체 아키텍처를 한 장으로 이해하기

[![3단계. 전체 아키텍처를 한 장으로 이해하기](/assets/images/agent-level-step-03-architecture.png)](/assets/images/agent-level-step-03-architecture.png)
*3단계. 전체 아키텍처를 한 장으로 이해하기 — 클릭하면 원본 크기로 볼 수 있습니다.*

제안 구조의 책임 경계는 명확하다.

| 구성요소 | 핵심 책임 | 하지 말아야 할 일 |
|---|---|---|
| Compiler | 선행조건·권한·제약·가용성을 검사해 허용 후보 생성 | 효용이 높다는 이유로 금지 행동 허용 |
| Router | 허용 후보 안에서 수준과 구체 행동 최적화 | 정책이나 권한을 임의로 변경 |
| Runtime | 최신 신뢰 상태에서 실제 실행을 강제 | Planner의 “허용” 선언만 믿고 실행 |
| Verifier | 실제 효과와 사후조건을 관측 가능한 증거로 확인 | 모델의 자연어 완료 선언을 증거로 간주 |

**실습 산출물:** 사용자 목표부터 상태 갱신까지 이어지는 A4 한 장 구조도.  
**통과 기준:** Compiler, Router, Runtime, Verifier를 보지 않고 3분 안에 그릴 수 있어야 한다.

## 4단계. 세 가지 정책 보존 불변조건 이해하기

[![4단계. 세 가지 정책 보존 불변조건 이해하기](/assets/images/agent-level-step-04-policy-invariants.png)](/assets/images/agent-level-step-04-policy-invariants.png)
*4단계. 세 가지 정책 보존 불변조건 이해하기 — 클릭하면 원본 크기로 볼 수 있습니다.*

Skill이나 다른 Agent로 실행을 넘길 때 다음 세 성질이 유지돼야 한다.

### Constraint Preservation

부모 업무에 남아 있는 미해결 필수 제약은 자식 업무에도 남아야 한다. “인증서 없이는 출하 금지”가 요약 과정에서 빠져서는 안 된다.

### Authority Non-Amplification

자식 권한은 부모가 조직 정책상 위임할 수 있는 범위를 넘을 수 없다. 부모의 직접 권한만 복사하는 것이 아니라, 공식 위임 관계와 범위까지 계산해야 한다.

### Goal Refinement

자식 목표는 부모 목표에 기여하는 유효한 하위 목표여야 한다. “지연 주문을 안전하게 해결”하는 업무에서 “분기 매출 확대”는 유효한 하위 목표가 아니다.

**실습 산출물:** 각 불변조건의 올바른 사례, 잘못된 전달 사례, Runtime 차단 사례.  
**통과 기준:** 위임 깊이가 늘어나도 미해결 제약과 유효한 권한 사슬이 유지되는 원리를 설명할 수 있어야 한다.

## 5단계. 추상화와 행동 집합 이해하기

[![5단계. 추상화와 행동 집합 이해하기](/assets/images/agent-level-step-05-abstraction-action-space.png)](/assets/images/agent-level-step-05-abstraction-action-space.png)
*5단계. 추상화와 행동 집합 이해하기 — 클릭하면 원본 크기로 볼 수 있습니다.*

전체 행동 공간은 다섯 수준의 합집합이다.

$$
\Omega = \Omega_T \cup \Omega_S \cup \Omega_D \cup \Omega_H \cup \Omega_C
$$

그러나 모든 행동이 매 순간 선택 가능한 것은 아니다. 시간 $t$의 상태에서 허용 판정을 통과한 행동만 실제 후보가 된다.

$$
\Omega_t^{adm} = \{\omega \in \Omega : M_t(\omega)=1\}
$$

이 구분은 매우 중요하다. **전체 Registry는 시스템이 알고 있는 Capability의 목록**이고, **허용 집합은 현재 상태·역할·정책·자원으로 실행 가능한 부분집합**이다.

**실습 산출물:** Tool 6개, Skill 3개, Delegation 2개, Human 2개, Control 3개로 구성된 작은 Registry.  
**통과 기준:** “전체 후보”와 “현재 허용 후보”를 분리해 설명할 수 있어야 한다.
