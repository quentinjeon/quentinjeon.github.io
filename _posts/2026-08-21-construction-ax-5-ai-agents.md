최근 건설사들과 AI 도입을 논의하면서 반복해서 듣게 되는 질문이 있습니다.

> "우리 회사 자료가 이미 많은데, AI가 그걸 알아서 찾아주게 할 수 없습니까?"

조금 더 들어가 보면 질문은 금방 달라집니다.

> "과거에 비슷한 문제가 있었을 때 어떻게 대응했는지 찾을 수 있습니까?"

그리고 그다음 질문은 이렇게 발전합니다.

> "찾는 것뿐 아니라, 그래서 지금 어떻게 해야 하는지도 알려줄 수 있습니까?"

여기서부터가 실제 **건설사 AX(AI Transformation)** 의 시작이라고 생각합니다.

![건설사 AX는 챗봇 구축이 아니다 — 회사의 지식을 찾고, 비교하고, 판단하고, 실행하게 만드는 것](/assets/images/2026-08-21/00-cover-find-to-act.png)

건설사에서 필요한 것은 단순한 사내 챗봇이 아닙니다.

기존 업무를 보면 사람이 반복적으로 하고 있는 일은 대체로 다음 여섯 가지입니다.

**Find → Compare → Decide → Generate → Connect → Act**

즉,

- 자료를 찾고
- 과거 사례와 비교하고
- 판단하고
- 결과물을 만들고
- 기존 시스템과 연결하고
- 실제 후속 업무를 실행합니다.

AI가 이 흐름 안으로 들어가야 비로소 AX가 됩니다.

---

## 1. 건설사 AX의 첫 번째 단계는 '통합 지식허브'다

대부분의 건설사는 이미 엄청난 양의 데이터를 가지고 있습니다.

문제는 데이터가 없다는 것이 아닙니다.

문제는 **너무 여러 곳에 흩어져 있다는 것**입니다.

예를 들어 회사 내부에는 다음과 같은 데이터가 존재합니다.

- 그룹웨어의 사내규정과 전자결재 문서
- ERP의 회계·자금·원가 정보
- 클라우드의 법무·소송자료
- 파일서버의 시방서와 매뉴얼
- 현장의 공사자료와 사진
- 개인 PC와 이메일에 남아 있는 과거 보고서

기존 방식에서는 담당자가 이 자료를 직접 찾습니다.

그러다 담당자가 퇴사하거나 부서를 이동하면 과거 경험까지 함께 사라지는 경우가 많습니다.

그래서 첫 번째 하위 시스템은 **통합 지식허브 & 검색 Agent**가 됩니다.

![하위 시스템 1. 통합 지식허브 &amp; 검색 Agent — 흩어진 자료를 다시 정리하지 않고, 현재 위치에서 연결·색인·검색하는 기업지식 기반](/assets/images/2026-08-21/01-knowledge-hub-agent.png)

구조는 다음과 같습니다.

```
기존 시스템
  → Connector
  → 문서 파싱 / OCR
  → Metadata 추출
  → 권한 기반 Indexing
  → Vector Search + Keyword Search
  → Knowledge Routing
  → 근거 기반 답변
```

여기서 중요한 것은 모든 자료를 새로운 시스템에 다시 업로드하는 것이 아닙니다.

가능하면 기존 그룹웨어, ERP, 파일서버, 클라우드를 그대로 두고 AI가 해당 위치를 연결하여 검색할 수 있도록 만드는 것이 좋습니다.

사용자는 단순하게 질문합니다.

> "욕실 방수 기준 어디 있지?"
>
> "3년 전에 OO현장에서 발생했던 하자 관련 자료 찾아줘."
>
> "이 내용과 관련된 결재문서와 첨부파일까지 보여줘."

AI는 답변만 생성하는 것이 아니라 반드시 **원문 문서와 근거 페이지까지 연결**해야 합니다.

건설사 AI에서는 이 부분이 특히 중요합니다.

AI가 맞는 말을 하는 것보다,

**"왜 이런 답변을 했는지 확인할 수 있는가"**

가 더 중요하기 때문입니다.

## 2. 법무·하자소송 Agent: 과거 사건을 현재 사건의 자산으로 만든다

건설사에서 AI의 ROI가 빠르게 나올 가능성이 높은 분야 중 하나가 법무와 하자입니다.

예를 들어 신규 하자소송이 발생했다고 가정해보겠습니다.

기존에는 담당자가 여러 자료를 찾습니다.

- 소장
- 준비서면
- 판결문
- 감정서
- 공사자료
- 과거 유사 사건
- 당시 대응자료

그리고 이를 사람이 직접 비교합니다.

![하위 시스템 2. 법무·하자 소송 대응 Agent — 판결문·감정서·소장·과거 대응사례를 연결하여 현재 사건의 Risk와 대응가이드를 빠르게 만드는 시스템](/assets/images/2026-08-21/02-legal-defect-agent.png)

AI를 적용하면 프로세스를 다음과 같이 바꿀 수 있습니다.

```
신규 사건 접수
  → 사건 문서 구조화
  → 유사 사건 검색
  → 주요 쟁점 추출
  → 감정금액 비교
  → 판결금액 비교
  → 주요 Risk 분석
  → 대응전략 추천
  → 보고서 초안 생성
```

예를 들어 사용자가 이렇게 질문할 수 있습니다.

> "이 사건과 유사한 판결 사례를 찾아줘."
>
> "감정금액과 실제 판결금액 차이가 컸던 사건을 찾아줘."

AI는 단순 검색 결과가 아니라,

**현재 사건 / 과거 사건 / 감정금액 / 판결금액 / 주요 쟁점 / 대응 결과**

를 하나의 비교 구조로 보여주는 것이 좋습니다.

이렇게 되면 법무 Agent는 단순 RAG 시스템이 아니라 **Case Intelligence System**에 가까워집니다.

특히 중요한 것은 법무팀뿐 아니라 CS·하자 담당 조직의 데이터를 같이 연결하는 것입니다.

법무에서는 사건으로 보고,

CS에서는 민원으로 보고,

현장에서는 시공 문제로 보던 하나의 이슈가 AI를 통해 연결될 수 있기 때문입니다.

## 3. 사내 시공지식 표준화 Agent: 현장마다 다른 판단을 줄인다

건설사에서 또 하나 큰 문제는 '기준의 분산'입니다.

현장 담당자가 어떤 시공 문제를 만났을 때 참고할 수 있는 자료가 여러 개입니다.

- 사내 시공지침
- 표준시방서
- 현장 시방서
- 도면
- 법규
- 품질기준
- 과거 현장 경험

문제는 이 기준들이 항상 완벽하게 일치하지 않는다는 것입니다.

현장 담당자가 실제로 궁금한 것은 결국 하나입니다.

> "그래서 우리 회사에서는 어떻게 해야 하는가?"

이 질문에 답하는 것이 **사내 시공지식 표준화 Agent**입니다.

![하위 시스템 3. 사내 시공지식 표준화 Agent — 본사 기준·시방서·도면·법규·현장 노하우를 하나의 회사 기준 답변으로 연결하는 표준 지식 시스템](/assets/images/2026-08-21/03-construction-standard-agent.png)

예를 들어 현장에서 질문합니다.

> "욕실 방수 시공 기준 알려줘."

AI는 단순히 인터넷이나 법규에서 답을 가져오는 것이 아니라,

```
사내 시공지침
  + 해당 프로젝트 시방서
  + 관련 도면
  + 법규
  + 과거 현장 사례
```

를 종합합니다.

그리고 최종적으로 다음과 같이 제공합니다.

- **회사 기준 답변**
- **근거 문서**
- **관련 도면**
- **관련 법규**
- **현장 점검 체크리스트**

여기서 중요한 것은 정보가 충돌할 경우입니다.

예를 들어 일반 법규 기준과 회사 내부 기준이 다를 수 있습니다.

따라서 시스템에는 반드시 **Knowledge Priority 정책**이 필요합니다.

예를 들어

```
프로젝트 계약조건
  → 프로젝트 시방서
  → 사내 기준
  → 법규
  → 일반 참고자료
```

처럼 정보의 우선순위를 정의해야 합니다.

이것이 제대로 정의되지 않으면 AI는 자료를 많이 찾더라도 회사의 기준을 제대로 답하지 못합니다.

## 4. 분양–입주–하자 Customer Journey Agent

다른 형태의 AX도 있습니다.

내부 지식을 개선하는 것이 아니라 **고객 접점 전체를 AI로 재설계하는 것**입니다.

건설사의 고객 접점은 보통 분리되어 있습니다.

```
분양 홈페이지
  → 상담센터
  → 계약관리
  → 입주시스템
  → 하자접수
  → AS센터
```

고객 입장에서는 하나의 건설사인데 시스템 입장에서는 여러 명의 고객처럼 관리되는 경우가 많습니다.

그래서 필요한 것은 **Customer Journey Agent**입니다.

![하위 시스템 4. 분양–입주–하자 Customer Journey Agent — 분양문의부터 계약·입주·하자접수·AS까지 고객 접점을 하나의 여정으로 연결하는 CX 시스템](/assets/images/2026-08-21/04-customer-journey-agent.png)

청약 전에는 분양 AI가 동·호수·평형·분양조건을 안내합니다.

계약 이후에는 고객 인증을 기반으로 계약자 전용 정보를 제공합니다.

입주 시점에는 입주 일정과 필요 서류를 안내합니다.

입주 이후에는 사진·음성·텍스트 기반으로 하자를 접수합니다.

AI는 접수된 내용을 분석해

- 하자 유형
- 위치
- 긴급도
- 담당 공종
- 담당 업체

를 판단하여 자동 Routing할 수 있습니다.

여기에 Web, App, AI Call, 상담센터를 통합하면 하나의 고객 프로필에 모든 상담 이력이 쌓이게 됩니다.

그때부터 AI는 단순 상담 도구가 아니라 **CX 운영 시스템**이 됩니다.

또한 고객 질문 데이터 자체가 새로운 자산이 됩니다.

예를 들어 분양 전 가장 많이 질문하는 내용,

입주자가 반복적으로 문의하는 항목,

특정 현장에서 반복되는 하자 유형을 분석하면

마케팅, 상품기획, 시공품질 개선까지 연결할 수 있습니다.

## 5. 입찰·공모지침 Risk Review Agent

제가 건설사 AX에서 특히 가치가 크다고 보는 영역 중 하나입니다.

건설사의 입찰에는 문서에 표현되지 않은 경험이 많이 들어갑니다.

예를 들어 경력자는 공모지침서나 ITB를 읽으면서 바로 감지합니다.

> "이 조항은 위험하다."
>
> "이 발주처에서는 예전에 이런 문제가 있었다."
>
> "이 조건으로 들어가면 원가 리스크가 크다."

문제는 이런 판단 기준이 대부분 사람의 머릿속에 있다는 것입니다.

AI가 이 노하우를 구조화할 수 있습니다.

![하위 시스템 5. 입찰·공모지침 Risk Review Agent — 공모지침서·ITB·계약조건을 과거 손실사례와 비교하여 독소조항과 Go/No-Go 판단 포인트를 찾는 시스템](/assets/images/2026-08-21/05-bid-risk-review-agent.png)

```
신규 ITB / RFP / 공모지침서
  → 조항 Parsing
  → 의무사항 구조화
  → 과거 프로젝트 검색
  → 과거 손실사례 검색
  → 독소조항 탐지
  → 발주처 특성 연결
  → Risk Score 계산
  → 검토 포인트 생성
  → Go / No-Go 판단 지원
```

여기서 핵심은 AI가 Go / No-Go를 대신 결정하는 것이 아닙니다.

AI의 역할은 **판단에 필요한 근거를 최대한 구조화해서 제공하는 것**입니다.

예를 들어 하나의 조항에 대해

```
위험 조항
  → 과거 유사 조항
  → 해당 프로젝트 손실 사례
  → 예상 영향
  → 검토 필요사항
```

을 연결합니다.

그러면 경력자의 경험이 개인 노하우에 머무르지 않고 조직의 지식으로 축적됩니다.

## 결국 건설사 AX는 6가지 능력으로 수렴한다

여러 건설사를 만나보면 요구사항은 서로 달라 보입니다.

하지만 한 단계 위에서 보면 대부분 다음 여섯 가지로 수렴합니다.

![건설사 유형별 핵심 니즈와 대표 Use Case — 건설사 니즈는 Find, Compare, Decide, Generate, Connect, Act 6개 축으로 정리된다](/assets/images/2026-08-21/06-needs-and-six-axes.png)

### 1. Find

> "우리 회사에 이 자료가 어디 있지?"

사내규정, 매뉴얼, 시방서, 과거 현장자료 검색

### 2. Compare

> "과거에는 어떻게 했지?"

과거 현장, 소송, 감정서, 판결문, 입찰 사례 비교

### 3. Decide

> "그래서 지금 어떻게 판단해야 하지?"

입찰 Go/No-Go, 법무 대응, 공사 의사결정 지원

### 4. Generate

> "이 자료를 보고 결과물을 만들어줘."

보고서, 체크리스트, 대응가이드, 검토의견 생성

### 5. Connect

> "ERP와 그룹웨어 자료를 다시 올리지 않고 사용할 수 없나?"

ERP, 그룹웨어, KMS, 클라우드, 파일서버 연결

### 6. Act

> "검색에서 끝내지 말고 실제 업무까지 해줘."

담당자 알림, 하자접수, 상담 연결, 보고 자동화

제가 생각하는 AX의 핵심은 마지막 **Act**입니다.

많은 기업의 AI 프로젝트가 Find에서 끝납니다.

검색을 잘하는 기업용 챗봇을 구축하고 프로젝트가 종료됩니다.

하지만 실제 생산성을 변화시키려면

```
Find → Compare → Decide → Generate → Connect → Act
```

까지 연결되어야 합니다.

## 건설사 AX를 설계할 때 반드시 고민해야 할 것

기능보다 먼저 결정해야 할 것이 있습니다.

### 첫째, 데이터가 어디에 있는가

문서가 있다고 해서 AI가 바로 사용할 수 있는 것은 아닙니다.

그룹웨어, ERP, NAS, 클라우드, 이메일 등 데이터 위치를 먼저 파악해야 합니다.

### 둘째, 누가 어떤 자료를 볼 수 있는가

건설사에는 민감한 정보가 많습니다.

- 원가
- 계약
- 법무
- 소송
- 개인정보
- 입찰자료

따라서 RAG보다 먼저 **RBAC와 권한 상속 구조**를 고민해야 할 수도 있습니다.

### 셋째, 답변의 근거를 어떻게 보여줄 것인가

특히 법무·품질·안전 영역에서는 AI 답변만 보여줘서는 안 됩니다.

문서명, 조항, 페이지, 원문을 함께 보여줘야 합니다.

### 넷째, 어떤 판단까지 AI에게 맡길 것인가

AI가 '관련자료를 찾아주는 것'과 '의사결정을 대신하는 것'은 전혀 다른 문제입니다.

고위험 업무에서는 AI가 판단 근거를 제공하고 최종 승인은 사람이 하는 **Human-in-the-loop** 구조가 현실적입니다.

### 다섯째, 기존 업무시스템과 어떻게 연결할 것인가

새로운 AI 화면 하나를 추가하는 것만으로는 AX가 되기 어렵습니다.

그룹웨어, ERP, CRM, 하자관리, 전자결재와 연결되어야 합니다.

AI가 결과를 생성한 다음 실제 업무를 실행하는 단계까지 연결해야 하기 때문입니다.

### 여섯째, 정확도를 무엇으로 측정할 것인가

단순히 "답변이 좋아 보인다"로 PoC를 평가하면 안 됩니다.

Use Case별로 다른 KPI가 필요합니다.

| Agent | KPI |
|---|---|
| 지식검색 Agent | 검색시간 |
| 법무 Agent | 유사사례 발견률 / 검토시간 |
| 시공지식 Agent | 기준 답변 일치율 |
| 하자 Agent | 자동 분류 정확도 / Routing 정확도 |
| 입찰 Agent | 위험조항 Recall |

## 그래서 PoC는 '전사 AI'보다 업무 하나에서 시작하는 것이 좋다

처음부터

> "전사 AI 플랫폼을 만들겠습니다."

라고 접근하면 범위가 지나치게 커집니다.

오히려

> "신규 하자소송이 들어왔을 때 과거 유사사건을 찾아주는 시스템"

처럼 명확한 업무 하나를 선정하는 것이 좋습니다.

그 업무에서

```
Input → Process → Decision → Output → Action
```

을 정의합니다.

그리고 이 구조가 제대로 작동하면 다른 업무로 확장합니다.

```
법무 Agent → 시공지식 Agent → 입찰 Agent → 고객 Agent
```

각 Agent는 다르지만 그 밑에는 동일한 기업 지식허브가 존재하게 됩니다.

결국 건설사 AX의 최종 모습은 수십 개의 독립적인 챗봇이 아니라,

**하나의 기업지식 기반 위에서 여러 업무 Agent가 움직이는 구조**

에 가까울 가능성이 높습니다.

## 결론

건설업은 AI를 적용하기 어려운 산업처럼 보일 수 있습니다.

하지만 반대로 생각하면 AI의 가치가 큰 산업이기도 합니다.

수십 년간 축적된 문서, 현장 경험, 법무 사례, 입찰 경험, 시공 기준, 고객 데이터가 존재하기 때문입니다.

문제는 지금까지 이 지식이 사람과 시스템 곳곳에 흩어져 있었다는 것입니다.

앞으로의 건설사 AX 경쟁력은 단순히 AI 모델을 얼마나 잘 쓰느냐보다,

**회사가 이미 가지고 있는 지식을 얼마나 잘 연결하고 재사용할 수 있는가**

에서 결정될 가능성이 큽니다.

그리고 그 구조는 결국 다음 한 문장으로 정리할 수 있습니다.

> **AI가 회사의 지식을 찾고(Find), 비교하고(Compare), 판단을 지원하고(Decide), 결과물을 만들고(Generate), 기존 시스템과 연결하고(Connect), 실제 업무까지 실행하게(Act) 만드는 것.**

이것이 제가 현재 건설사 AX를 바라보는 기본 프레임입니다.
