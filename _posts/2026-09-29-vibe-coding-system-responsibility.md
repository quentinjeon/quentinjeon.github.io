> **한 문장 요약**
> AI가 만든 코드의 모든 줄을 설명하지 못해도 시스템을 만들 수 있다.
> 다만 배포하는 사람은 그 시스템이 무엇을 하고, 어디에서 실패하며,
> 실패를 어떻게 발견하고 멈추고 되돌릴지를 설명할 수 있어야 한다.

![AI가 코드를 작성하는 시대, 인간의 책임은 어디에 남아야 하는가](/assets/images/vibe-coding-01-responsibility-question.jpg)

## 1. AI가 코드를 짜기 시작하자, 책임의 기준이 흔들리기 시작했다

Cursor, Claude Code, Codex 같은 AI 코딩 도구를 사용하면 과거에는 몇 시간 혹은 며칠이 걸리던 기능을 훨씬 빠르게 구현할 수 있다. 이제는 기획자가 자연어로 요구사항을 설명하고, AI가 프로젝트 구조를 만들고, API를 연결하고, 데이터베이스 코드를 작성하고, 화면까지 구현하는 일이 낯설지 않다.

그런데 생산성이 올라갈수록 오히려 불편한 질문이 생긴다. **"내가 이 코드의 모든 줄을 이해하지 못하는데, 이 프로그램을 배포해도 되는가?"** 라는 질문이다.

이 질문을 단순히 "개발 공부를 더 해야 한다"는 문제로만 보면 바이브 코딩의 본질을 놓치기 쉽다. 실제 쟁점은 코드 지식의 양보다 더 근본적이다. AI가 구현을 대신하는 환경에서 인간은 무엇을 알고 있어야 하며, 어디까지 책임져야 하는가의 문제다.

> **핵심 질문**
> 책임을 질 수 있으려면 구현의 모든 세부 사항을 알아야 할까?
> 아니면 시스템의 목적, 동작, 실패 조건과 통제 방법을 이해하는 것으로도 충분할까?

## 2. 우리는 이미 "내부를 다 모르는 기술"을 매일 사용한다

생각해보면 인간은 오래전부터 내부 원리를 완전히 이해하지 못하는 수많은 도구를 사용해 왔다. 자동차를 운전한다고 해서 엔진의 연소 과정과 ECU의 모든 소프트웨어를 설명할 필요는 없다. 펌프로 물을 옮기는 사람이 유체역학과 임펠러 설계를 완벽히 이해해야 하는 것도 아니다. 스마트폰 사용자는 반도체 구조, 운영체제 커널, 통신 프로토콜을 모두 알지 못한다.

소프트웨어 개발도 이미 마찬가지다. 웹서비스를 만드는 개발자가 브라우저 엔진, Linux 커널, CPU 명령어, 클라우드 데이터센터의 네트워크 장비까지 전부 설명할 수는 없다. 라이브러리와 프레임워크는 바로 이런 복잡성을 감추기 위해 존재한다.

![인간은 오래전부터 내부 원리를 모두 알지 못하는 도구를 사용해 왔다](/assets/images/vibe-coding-02-tools-we-dont-fully-know.jpg)

그럼에도 우리는 이 기술들을 사용할 수 있다. 이유는 단순하다. 내부 구현 전체를 몰라도 "무엇을 넣으면 무엇이 나오고, 어느 범위에서 정상 작동하며, 문제가 생기면 어떻게 대응해야 하는가"를 이해하고 있기 때문이다.

펌프를 예로 들면 사용자는 내부 설계를 몰라도 최소한 A 지점의 물을 B 지점으로 보낸다는 목적, 허용 압력과 유량, 누수나 과열 같은 대표적 위험, 비상 시 정지 방법은 알아야 한다. 즉, 인간은 Implementation 전체가 아니라 **System의 역할과 경계**를 이해하는 방식으로 기술을 사용해 왔다.

## 3. "코드를 안다"와 "시스템을 안다"는 다른 능력이다

바이브 코딩에서 가장 먼저 구분해야 할 것은 코드 수준의 이해와 시스템 수준의 이해다. 코드 수준의 이해는 함수, 클래스, 라이브러리, 예외 처리, 내부 알고리즘을 세부적으로 파악하는 것이다. 시스템 수준의 이해는 이 구성요소들이 어떤 목적을 위해 연결되고, 어떤 입력을 받아 어떤 결과를 만들며, 어떤 조건에서 문제가 생기는지를 파악하는 것이다.

![코드 전체 이해보다 먼저 확인해야 할 시스템 이해의 기준](/assets/images/vibe-coding-03-what-system-understanding-means.jpg)

예를 들어 고객 문의를 처리하는 AI 시스템을 생각해보자. 실제 구현은 수천 줄의 코드와 여러 라이브러리, API, 데이터베이스, LLM 호출로 구성될 수 있다. 하지만 시스템 관점에서는 다음과 같이 설명할 수 있다.

- **입력(Input)**: 고객의 질문, 계정 정보, 첨부 데이터
- **처리(Process)**: 문의 분류 → 권한 확인 → 관련 데이터 검색 → 답변 생성
- **출력(Output)**: 고객에게 전달되는 답변 또는 상담원 전환
- **정상 범위**: 지원하는 문의 유형, 사용할 수 있는 데이터 범위, 허용된 행동
- **실패 조건**: 잘못된 분류, 잘못된 데이터 조회, 환각, API 장애, 권한 오류
- **통제 방법**: 자동 차단, 사람 승인, 로그 확인, 기능 비활성화, 롤백

이 정도를 정확히 설명할 수 있다면 모든 코드를 직접 작성하지 않았더라도 그 시스템을 상당한 수준에서 이해하고 있다고 볼 수 있다. 반대로 코드 몇백 줄을 읽었다고 해서 시스템 전체의 데이터 흐름, 권한, 외부 의존성, 운영 위험을 모른다면 실제로는 시스템을 충분히 이해하지 못한 것일 수 있다.

## 4. AI 시대에는 IPO만으로 부족하다

기획이나 시스템 설계에서는 흔히 IPO, 즉 Input-Process-Output으로 구조를 본다. 무엇이 들어오고, 어떻게 처리되고, 무엇이 나오는지를 정의하는 방식이다. AI로 만든 시스템을 실제 운영 환경에 배포하려면 여기에 세 가지를 추가하는 것이 좋다.

> **AI 시대의 최소 시스템 프레임**
> Input → Process → Output → **Failure → Monitoring → Control**

### Failure: 어떻게 실패할 수 있는가

대표적인 실패 모드를 사전에 정의해야 한다. 잘못된 답변, 권한 초과, 데이터 누락, 중복 처리, 외부 API 장애, 예상하지 못한 사용자 입력 등이다. 중요한 것은 "에러가 날 수 있다"는 추상적인 말이 아니라 **어떤 실패가 어떤 피해로 이어지는지**를 구체적으로 적는 것이다.

### Monitoring: 실패했다는 사실을 어떻게 발견할 것인가

사람이 모든 실행을 지켜볼 수는 없다. 그래서 로그, 오류율, 응답 시간, 이상 응답 비율, 권한 오류, 사용자 신고 같은 관찰 지표가 필요하다. 시스템이 잘못되었을 때 "누군가 우연히 발견하기 전까지" 모르고 있는 구조는 운영 가능한 시스템이라고 보기 어렵다.

### Control: 문제가 생기면 어떻게 멈출 것인가

특정 기능을 끌 수 있는 Feature Flag, 이전 버전으로 되돌리는 Rollback, 위험한 요청을 사람에게 보내는 Escalation, 관리자 Override, 사용 권한 차단처럼 통제 수단이 필요하다. 인간의 책임은 모든 실행을 직접 수행하는 데서 발생하는 것이 아니라, **필요할 때 개입할 수 있는 실질적인 통제권을 갖는 데서** 발생한다.

## 5. Explainability보다 더 실무적인 질문

AI 논의에서는 설명 가능성(Explainability)이 자주 강조된다. 왜 이런 판단을 했는가, 왜 이런 결과가 나왔는가를 설명할 수 있어야 한다는 개념이다. 물론 중요하다. 그러나 실제 운영에서는 설명 가능성만으로 충분하지 않다.

| | 질문 |
|---|---|
| **Explainability** | 왜 이런 결과가 나왔는가? |
| **Observability** | 지금 시스템에서 무슨 일이 일어나고 있는가? |
| **Controllability** | 문제가 생겼을 때 사람이 실제로 멈추거나 수정할 수 있는가? |

특히 비결정적이고 복잡한 AI 시스템에서는 모든 결과를 완벽하게 설명하는 것이 어려울 수 있다. 그럴수록 운영자는 시스템 상태를 관찰하고 위험 행동을 제한하며 필요하면 즉시 차단할 수 있어야 한다. 실무적으로는 "완벽하게 설명할 수 있는가?"만큼 **"이상 동작을 발견할 수 있는가?"** 와 **"발견했을 때 통제할 수 있는가?"** 가 중요하다.

## 6. Human-in-the-Loop는 사람이 AI의 모든 일을 다시 하는 것이 아니다

Human-in-the-Loop를 "AI가 만든 모든 결과를 사람이 마지막에 한 번씩 확인하는 것"으로만 이해하면 AI가 만들어낸 생산성의 상당 부분이 다시 검토 비용으로 사라진다. AI가 코드 3,000줄을 만들고 사람이 3,000줄을 전부 읽은 다음 배포해야 한다면, 자동화의 효과는 크게 줄어든다.

![Human-in-the-Loop를 모든 작업의 수동 검토가 아니라 통제권 유지로 보는 관점](/assets/images/vibe-coding-04-human-in-the-loop.jpg)

따라서 Human-in-the-Loop를 더 넓게 볼 필요가 있다. 인간의 핵심 역할은 모든 작업을 직접 수행하는 것이 아니라, **책임이 필요한 의사결정 지점과 통제 지점에 존재하는 것**이다.

- AI가 반복적이고 대량의 작업을 수행한다.
- 자동 테스트와 정책 검증이 일차적으로 위험을 걸러낸다.
- 고위험이거나 불확실한 경우 사람에게 Escalation한다.
- 배포, 결제, 삭제, 권한 변경 등 중요한 행동에는 승인 절차를 둔다.
- 운영 중 이상 징후를 모니터링하고 필요할 때 사람이 개입한다.

이 관점에서 좋은 Human-in-the-Loop는 "사람이 매번 루프 안에서 일한다"는 의미보다는 **"인간이 최종적으로 시스템의 경계와 통제권을 유지한다"** 는 의미에 가깝다.

## 7. 하지만 모든 시스템에 같은 검증 기준을 적용하면 안 된다

여기서 중요한 반론이 생긴다. "그렇다면 AI가 만든 코드도 대충 동작만 확인하면 배포해도 된다는 뜻인가?" 그렇지 않다. 핵심은 **검증의 수준을 시스템의 위험도에 맞추는 것**이다.

![AI 시스템의 검증 수준은 위험도에 따라 달라져야 한다](/assets/images/vibe-coding-05-risk-based-verification.jpg)

사내 대시보드의 그래프 색상이 잘못 표시되는 것과 결제 시스템이 중복 결제를 일으키는 것은 같은 문제가 아니다. 마케팅 문구 생성기의 오탈자와 의료 의사결정 시스템의 잘못된 추천 역시 동일한 기준으로 다룰 수 없다.

> **위험 기반 검증의 직관적 공식**
> 필요한 검증 수준 ≈ 실패 가능성 × 실패 영향 × 되돌릴 수 없는 정도

이 공식은 수학적으로 정확한 계산식을 뜻하기보다 검증 강도를 정하는 **사고 프레임**이다. 실패가 자주 일어나고, 피해가 크며, 한 번 실행하면 되돌리기 어려울수록 더 강한 테스트, 리뷰, 승인, 모니터링이 필요하다.

| 시스템 예시 | 위험 수준 | 권장 검증 방식 |
|---|---|---|
| 사내 업무 대시보드 | 낮음 | 자동 테스트 + 화면 확인 + 롤백 |
| 마케팅 콘텐츠 생성기 | 낮음~중간 | 샘플 검토 + 금칙어/정책 필터 |
| 고객 FAQ 챗봇 | 중간 | 평가셋 + 모니터링 + 상담원 전환 |
| 결제/환불 시스템 | 높음 | 통합 테스트 + 보안 검증 + 승인 절차 |
| 개인정보 처리 | 높음 | 권한·로그·감사 + 최소 접근 + 법적 검토 |
| 대출·의료 등 중대한 의사결정 | 매우 높음 | 강한 검증 + 인간 승인 + 지속적 감사 |

## 8. 약의 비유가 중요한 이유

약은 이 문제를 생각할 때 좋은 비유다. 대부분의 환자는 약의 분자 구조, 수용체 작용, 대사 경로를 모두 이해하지 않는다. 그렇다고 아무 약이나 만들어 바로 복용하지도 않는다. 내부 원리의 완전한 이해를 모든 사용자에게 요구하는 대신 임상시험, 허가, 용량, 금기사항, 부작용 보고, 처방 기준 같은 **검증 체계**를 만든다.

AI 소프트웨어도 비슷한 방향으로 발전할 수 있다. "배포자가 모든 코드를 읽었는가?" 하나만을 안전의 기준으로 삼는 대신 테스트, 격리 환경, 권한 관리, 정책 검사, 모니터링, 감사 로그, 롤백, 승인 절차 등 여러 층의 안전장치를 설계하는 것이다.

> **중요한 전환**
> 사람의 이해 부족을 방치하는 것이 아니라,
> 사람이 모든 세부 구현을 이해하지 않아도 위험을 통제할 수 있도록 검증 체계를 설계하는 것이다.

## 9. 그렇다면 코드 공부는 필요 없어지는가?

여기까지 읽으면 "앞으로는 코드를 몰라도 된다는 이야기인가?"라는 질문이 나올 수 있다. 답은 아니다. 코드를 이해하는 능력은 여전히 중요하다. 오히려 복잡하고 위험한 시스템일수록 기술적 이해는 더 큰 가치를 가진다.

코드를 잘 이해하면 AI가 잘못 만든 구조를 빠르게 발견할 수 있고, 성능 병목과 보안 문제를 더 깊게 분석할 수 있으며, 문제가 생겼을 때 원인까지 추적할 수 있다. 중요한 것은 코드 이해를 **"배포 자격의 절대 조건"과 동일시하지 않는 것**이다.

AI 시대에는 전문성의 층위가 다양해질 수 있다. 어떤 사람은 내부 구현까지 깊게 이해하는 엔지니어가 되고, 어떤 사람은 여러 컴포넌트를 조합해 시스템을 설계하는 사람이 되고, 또 어떤 사람은 비즈니스 문제와 시스템 위험을 연결하는 역할을 맡을 수 있다. 모두에게 같은 깊이의 구현 지식을 요구하는 것은 현실적인 기준이 아닐 수 있다.

## 10. 바이브 코딩 시대의 최소 책임 기준 10가지

그렇다면 AI에게 상당 부분의 구현을 맡기더라도 최소한 무엇을 알아야 할까. 실제 배포 전에 다음 열 가지 질문에 답할 수 있는지를 확인하는 것이 실용적인 기준이 될 수 있다.

1. 이 시스템은 정확히 어떤 문제를 해결하는가?
2. 입력되는 데이터와 출력되는 결과는 무엇인가?
3. 어떤 데이터베이스, API, 파일, 외부 서비스에 접근하는가?
4. 누가 어떤 기능과 데이터에 접근할 수 있는가?
5. 정상적으로 동작하는 범위와 지원하지 않는 범위는 어디인가?
6. 대표적인 실패 모드와 오작동 시나리오는 무엇인가?
7. 실패하면 사용자·회사·데이터에 어떤 피해가 발생할 수 있는가?
8. 그 실패를 로그나 지표를 통해 발견할 수 있는가?
9. 문제가 발생하면 기능을 중단하거나 이전 버전으로 되돌릴 수 있는가?
10. 어떤 위험 수준부터 사람의 승인이나 추가 검증이 필요한가?

이 질문에 답하지 못한다면 "코드를 모른다"는 것보다 더 큰 문제가 있다. 시스템 자체를 모른 채 배포하는 것이기 때문이다. 반대로 이 질문에 답하고 검증 수단까지 갖추고 있다면 AI가 구현의 상당 부분을 담당했더라도 최소한 무엇을 세상에 내보내는지는 알고 있다고 볼 수 있다.

## 11. Implementation Owner에서 System Owner로

![AI 시대 개발자의 역할은 구현자에서 시스템 책임자로 확장된다](/assets/images/vibe-coding-06-implementation-to-system-owner.jpg)

기존 개발 흐름은 문제 정의 → 직접 구현 → 코드 리뷰 → 테스트 → 배포에 가까웠다. AI 코딩이 본격화되면 사람의 위치가 조금 달라진다. 문제를 정의하고, 시스템 구조와 경계를 정하고, AI에게 구현을 맡기고, 자동화된 검증을 설계하고, 위험한 행동의 승인 지점을 정의하고, 운영 상태를 관찰하는 역할이 더 중요해진다.

즉 개발자의 역할이 사라지는 것이 아니라 **추상화 수준이 올라가는 것**이다. Implementation Owner에서 System Owner로, "모든 줄을 직접 작성하는 사람"에서 "전체 시스템의 목적과 경계와 위험을 책임지는 사람"으로 역할이 확장되는 셈이다.

> **이 글의 결론**
> Human writes every line이 아니라, **Human remains in control.**
> AI가 코드를 작성하더라도 목적은 사람이 정하고, 위험의 경계는 사람이 설정하며,
> 최종 통제권은 사람이 가져야 한다.

## 12. 결론: 책임의 단위를 코드에서 시스템으로 옮겨야 한다

컴퓨터의 역사는 계속해서 복잡성을 추상화해 온 역사이기도 하다. 기계어에서 고급 언어로, 직접 구현에서 라이브러리와 프레임워크로, 물리 서버에서 클라우드로 이동하면서 인간은 아래 계층의 모든 세부사항을 몰라도 더 큰 시스템을 만들 수 있게 됐다.

생성형 AI와 바이브 코딩은 이 추상화를 한 단계 더 밀어붙인다. 이제는 구현 코드 자체도 AI가 상당 부분 만들어낼 수 있다. 그렇다면 책임의 기준 역시 새로운 추상화 수준에 맞게 바뀔 필요가 있다.

모든 코드를 설명할 수 있어야 책임질 수 있다는 기준은 점점 현실성이 떨어질 수 있다. 대신 배포하는 사람은 시스템의 목적, 입력과 출력, 데이터 접근, 실패 방식, 피해 범위, 관찰 방법, 중단과 복구 방법을 설명할 수 있어야 한다. 위험도가 높을수록 검증과 인간 개입 수준도 높아져야 한다.

결국 바이브 코딩의 핵심 질문은 "내가 이 코드를 전부 아는가?"가 아니다. 더 중요한 질문은 **"내가 이 시스템이 무엇을 하는지 알고 있으며, 잘못되었을 때 그것을 발견하고 책임 있게 통제할 수 있는가?"** 다.

> AI 시대의 개발자에게 필요한 것은 모든 코드를 암기하는 능력이 아니라,
> AI가 만든 복잡성을 구조화하고 검증하며 통제하는 능력일지도 모른다.
