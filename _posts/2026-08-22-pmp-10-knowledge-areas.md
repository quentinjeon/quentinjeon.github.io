프로젝트가 실패하는 이유는 단순히 개발력이 부족해서가 아닙니다.

기술적으로는 완성됐지만 고객의 공식 승인을 받지 못할 수 있고, 요구사항은 명확하지만 일정이 무너질 수 있습니다. 품질은 좋지만 예산이 초과되기도 하고, 계획대로 구축했지만 현업이 사용하지 않는 경우도 있습니다.

이 문제들은 각각 다른 관리영역의 누락에서 발생합니다.

PMP의 10대 지식영역은 프로젝트를 다음 열 가지 질문으로 바라보게 합니다.

> **전체를 어떻게 맞출 것인가, 무엇을 할 것인가, 언제 할 것인가, 얼마를 쓸 것인가, 어느 수준으로 만들 것인가, 누가 수행할 것인가, 정보를 어떻게 흐르게 할 것인가, 불확실성에 어떻게 대비할 것인가, 외부에서 무엇을 확보할 것인가, 누구의 지지와 승인을 얻을 것인가.**

이를 간단히 정리하면 다음과 같습니다.

```text
전체        → 통합관리
무엇        → 범위관리
언제        → 일정관리
얼마        → 원가관리
어느 수준   → 품질관리
누가        → 자원관리
어떤 정보   → 의사소통관리
만약에      → 리스크관리
외부에서    → 조달관리
누구의 지지 → 이해관계자관리
```

이 글에서 다루는 10대 지식영역은 PMBOK의 예측형 프로젝트관리 프로세스 모델을 기반으로 합니다. 최신 프로젝트관리 체계는 원칙·성과영역·애자일·하이브리드 접근까지 포괄하지만, 10대 지식영역은 프로젝트를 빠짐없이 설계하고 점검하는 실무 프레임으로 여전히 유효합니다.

## 1. 프로젝트 통합관리: 전체를 하나로 맞추는 컨트롤타워

[![PMP 01 프로젝트 통합관리 인포그래픽](/assets/images/pmp-01-integration.png)](/assets/images/pmp-01-integration.png)

*그림 1. 프로젝트 전체 목표, 계획, 실행, 변경, 종료를 연결하는 통합관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

통합관리는 나머지 9개 지식영역을 하나의 프로젝트 시스템으로 연결하는 영역입니다.

범위는 더 많은 기능을 요구하고, 일정은 더 빠른 완료를 요구하며, 원가는 비용 절감을 요구하고, 품질은 더 많은 검증을 요구합니다. 통합관리의 역할은 이러한 충돌을 프로젝트 전체 관점에서 조정하는 것입니다.

핵심은 **변경을 막는 것**이 아니라 **변경의 영향을 분석하고 공식적으로 결정하는 것**입니다.

```text
변경 요청
→ 범위·일정·원가·품질·자원·리스크 영향 분석
→ 승인·거절·보류
→ 계획과 기준선 갱신
→ 실행
→ 결과 확인
→ 이해관계자 통보
```

예를 들어 스마트글래스 프로젝트 도중 iOS SDK, AI 양방향 음성대화, 전화 수신·종료, OTA 업데이트가 추가로 요구됐다고 가정해보겠습니다.

이 요청을 곧바로 개발에 반영하면 안 됩니다. 기존 계약 범위인지, 납기 연장이 필요한지, 추가 개발비와 테스트비가 발생하는지, 펌웨어·블루투스 인력이 필요한지, 벤더가 실제로 지원할 수 있는지를 종합 판단한 뒤 변경을 승인해야 합니다.

대표 산출물은 다음과 같습니다.

- Project Charter
- Project Management Plan
- Change Log
- Lessons Learned
- Closing Report

프로젝트 헌장이 없거나 승인권자가 불명확하고, 변경은 계속 발생하지만 일정과 예산이 그대로라면 통합관리가 무너지고 있다는 신호입니다.

## 2. 프로젝트 범위관리: 무엇을 하고 무엇을 하지 않을지 정한다

[![PMP 02 프로젝트 범위관리 인포그래픽](/assets/images/pmp-02-scope.png)](/assets/images/pmp-02-scope.png)

*그림 2. 요구사항을 범위·WBS·검수·변경통제로 연결하는 범위관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

범위관리는 프로젝트가 완료됐다고 인정받기 위해 정확히 무엇을 만들어야 하는지, 그리고 무엇은 만들지 않는지를 정의합니다.

여기서 반드시 구분해야 하는 것이 **제품 범위**와 **프로젝트 범위**입니다.

### 제품 범위

최종 결과물의 기능과 특성입니다.

기업 RAG 챗봇이라면 다음 항목들이 제품 범위에 해당합니다.

- PDF 문서 업로드
- RAG 기반 질의응답
- 답변 근거 표시
- 사용자 권한관리
- 상담원 연결

### 프로젝트 범위

제품을 만들기 위해 프로젝트팀이 수행해야 하는 전체 작업입니다.

- 현업 인터뷰
- 요구사항 분석
- 데이터 수집
- 데이터 정제
- 아키텍처 설계
- 개발
- 테스트
- 사용자 교육
- 운영 인계

제품 기능만 정의하고 데이터 수집, 테스트, 교육, 보안 검토와 운영 인계를 누락한다면 프로젝트 범위가 불완전한 것입니다.

범위관리의 중심 산출물은 다음 두 가지입니다.

- **WBS**: 전체 프로젝트 범위를 산출물 중심으로 계층 분해한 구조
- **요구사항 추적 매트릭스**: 요구사항의 출처, 구현 기능, 테스트 방법, 승인 상태를 연결한 표

WBS는 상위 범위의 전체 작업을 빠짐없이 포함하는 100% 규칙을 따라야 합니다. 또한 “제외 범위”를 명확히 적어야 Scope Creep을 막을 수 있습니다.

고객이 무엇을 기준으로 검수할지도 프로젝트 초기에 합의해야 합니다. 기술적으로 잘 만들었다고 해서 고객의 공식 인수가 자동으로 완료되는 것은 아닙니다.

## 3. 프로젝트 일정관리: 날짜표가 아니라 의존관계의 설계

[![PMP 03 프로젝트 일정관리 인포그래픽](/assets/images/pmp-03-schedule.png)](/assets/images/pmp-03-schedule.png)

*그림 3. 활동·의존관계·기간·주공정·기준선을 연결하는 일정관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

일정관리는 단순히 시작일과 종료일을 적는 작업이 아닙니다.

실행 가능한 일정은 다음 요소가 함께 있어야 합니다.

```text
활동
+ 순서
+ 의존성
+ 소요기간
+ 자원 가용성
+ 리스크
= 실행 가능한 일정
```

먼저 WBS의 작업 패키지를 실제 수행 가능한 활동으로 나누고, 선후행 관계를 정의합니다. 그다음 활동별 기간을 산정하고 주공정, 즉 Critical Path를 확인한 뒤 승인된 일정 기준선을 만듭니다.

프로젝트가 시작된 이후에는 현재 일정과 기준선의 차이를 지속적으로 추적해야 합니다.

AX 프로젝트에서는 개발일정보다 고객 의존 일정이 더 큰 병목이 되기도 합니다.

- 고객 데이터 제공
- 개인정보·보안 승인
- API 발급
- 벤더 SDK 제공
- 현업 인터뷰
- UAT 사용자 배정
- 검수기준 합의
- 고객 의사결정

따라서 개발팀의 업무 일정만 관리해서는 안 됩니다. 고객이 제공해야 하는 데이터와 승인 일정도 별도의 마일스톤과 의존관계로 관리해야 합니다.

Fast Tracking은 원래 순차적으로 해야 할 작업을 병렬화해 시간을 줄이지만 재작업 위험을 높입니다. Crashing은 인력과 비용을 추가해 기간을 줄이지만 원가와 커뮤니케이션 복잡성을 증가시킵니다.

일정 단축은 언제나 원가와 리스크를 함께 보고 판단해야 합니다.

## 4. 프로젝트 원가관리: 구축비보다 총비용을 본다

[![PMP 04 프로젝트 원가관리 인포그래픽](/assets/images/pmp-04-cost.png)](/assets/images/pmp-04-cost.png)

*그림 4. 원가산정·예산·기준선·집행·예측을 연결하는 원가관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

원가관리는 프로젝트에 필요한 비용을 산정하고 예산 기준선을 수립한 뒤, 실제 비용과 계획 비용의 차이를 통제하는 영역입니다.

AI·AX 프로젝트에서는 개발비만 계산하면 안 됩니다.

- 내부 인건비
- 외주 개발비
- 프로젝트관리비
- 데이터 정제비
- API 비용
- 클라우드 비용
- Vector DB 비용
- 테스트·보안 비용
- 장비 구매비
- 교육비
- 운영·유지보수비
- 예비비

특히 AI 도입 효과는 다음처럼 구분해야 합니다.

### Hard Saving

실제 지출이 감소한 금액입니다.

### Capacity Gain

동일한 인력으로 더 많은 업무를 처리하게 된 효과입니다.

### Quality Gain

오류와 재작업이 줄어든 효과입니다.

### Risk Avoidance

안전사고, 법적 분쟁, 품질사고와 같은 손실 가능성이 낮아진 효과입니다.

### Revenue Impact

매출, 전환율 또는 고객 유지율이 증가한 효과입니다.

직원의 업무시간이 1,000시간 줄었다고 해서 그만큼 현금이 바로 절감된 것은 아닙니다. 인원을 감축하거나 외주비를 줄이지 않았다면 이는 주로 처리역량 증가에 해당합니다.

이 구분이 없으면 AI 프로젝트의 ROI가 과대평가됩니다.

원가 통제에서는 Cost Baseline과 실제 발생비용을 비교하고, 필요하면 CPI·CV와 같은 획득가치 지표를 활용해 향후 완료비용을 예측합니다.

## 5. 프로젝트 품질관리: ‘잘 만든 것’이 아니라 ‘합의한 기준을 충족한 것’

[![PMP 05 프로젝트 품질관리 인포그래픽](/assets/images/pmp-05-quality.png)](/assets/images/pmp-05-quality.png)

*그림 5. 품질기준·프로세스·테스트·결함·수용을 연결하는 품질관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

품질은 기능이 많거나 고급스러워 보이는 상태를 의미하지 않습니다.

핵심 질문은 다음입니다.

> **합의된 요구사항과 수용기준을 일관되게 충족하는가?**

품질관리는 세 단계로 나뉩니다.

1. **품질관리 계획수립**: 무엇을 좋은 품질로 볼지 정의
2. **품질 관리**: 좋은 결과가 나오도록 작업 프로세스를 관리
3. **품질 통제**: 실제 산출물이 기준을 충족하는지 검사

AI 시스템에서는 일반 기능 테스트만으로 부족합니다.

### 검색 품질

- Recall@K
- Precision@K
- MRR
- NDCG

### 답변 품질

- Correctness
- Groundedness
- Relevance
- Completeness
- Citation Accuracy

### 운영 품질

- 평균 응답시간
- 오류율
- 폴백률
- 상담원 전환율
- 재질문율
- 사용자 만족도

“AI가 대체로 잘 답한다”는 표현은 품질기준이 아닙니다.

예를 들어 다음과 같이 측정 가능한 기준이 필요합니다.

- Top-3 Recall 80% 이상
- 답변 근거 표시율 100%
- 평균 응답시간 5초 이하
- 개인정보 노출 0건
- 치명적 환각 1% 이하

또한 일반 오류와 치명적 오류를 구분해야 합니다. 법무, 안전, 금융, 설비제어와 관련된 오류는 평균 정확도가 높더라도 별도의 기준으로 관리해야 합니다.

## 6. 프로젝트 자원관리: 사람뿐 아니라 장비·계정·환경까지 관리한다

[![PMP 06 프로젝트 자원관리 인포그래픽](/assets/images/pmp-06-resource.png)](/assets/images/pmp-06-resource.png)

*그림 6. 역할정의·자원산정·확보·배치·팀관리·통제를 연결하는 자원관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

자원관리는 프로젝트에 필요한 사람과 물적 자원을 계획하고 확보하고 관리하는 영역입니다.

### 팀 자원

- PM
- 기획자
- 개발자
- 데이터 엔지니어
- AI 엔지니어
- 디자이너
- QA
- 현업 담당자
- 보안 담당자

### 물적 자원

- 서버
- GPU
- 테스트 장비
- 스마트글래스
- 개발 계정
- 회의실
- 라이선스
- 운영환경

대표적인 역할관리 도구는 RACI입니다.

```text
R Responsible  실제 수행자
A Accountable  최종 책임자·승인자
C Consulted    사전 협의 대상
I Informed     결과 통보 대상
```

한 업무에 수행자는 여러 명일 수 있지만 최종 책임자와 승인권자가 지나치게 많으면 결정이 지연됩니다. 반대로 담당자는 있는데 승인권자가 없으면 산출물이 끝없이 보류됩니다.

한 사람이 인터뷰, 제안, 교육, PRD, PoC 설계, 보고서, 검수까지 전부 수행하는 구조는 단기적으로 빠를 수 있습니다.

그러나 이는 Bus Factor 1, 즉 한 명이 빠지면 프로젝트가 중단되는 구조입니다.

이를 줄이려면 다음 운영장치가 필요합니다.

- 인터뷰 템플릿 표준화
- PRD 양식 표준화
- 문서 저장소 통일
- 대체 검토자 지정
- 개발·데이터 담당자 역할 분리
- 주간별 실제 가용시간 확인
- 핵심 지식의 문서화와 인수인계

## 7. 프로젝트 의사소통관리: 많이 말하는 것이 아니라 결정 가능하게 전달한다

[![PMP 07 프로젝트 의사소통관리 인포그래픽](/assets/images/pmp-07-communication.png)](/assets/images/pmp-07-communication.png)

*그림 7. 대상·메시지·채널·공유·피드백을 연결하는 의사소통관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

의사소통관리는 필요한 정보가 필요한 사람에게 적절한 시점·형식·채널로 전달되도록 설계하는 영역입니다.

핵심은 정보의 양이 아니라 **의사결정 가능성**입니다.

프로젝트에서는 대상마다 필요한 정보가 다릅니다.

- 스폰서: 일정·비용·주요 위험·의사결정 요청
- 현업팀: 개발상태·업무변경·테스트 요청
- 개발팀: 요구사항·우선순위·변경사항
- 보안팀: 데이터 흐름·권한·개인정보 이슈
- 기관 담당자: 진척률·산출물·사업계획 대비 상태

의사소통 방식은 세 가지로 나눌 수 있습니다.

### Interactive

회의, 전화, 화상회의, 워크숍처럼 실시간 상호작용이 가능한 방식입니다.

### Push

이메일, 보고서, 알림, 메신저처럼 특정 대상에게 정보를 발송하는 방식입니다.

### Pull

위키, 문서저장소, 대시보드, 지식베이스처럼 필요한 사람이 정보를 조회하는 방식입니다.

좋은 상태보고서는 업무 나열에 그치지 않습니다.

```text
1. 전체 상태
2. 지난 기간 완료사항
3. 다음 기간 계획
4. 일정 기준선 대비 차이
5. 비용 기준선 대비 차이
6. 리스크와 이슈
7. 변경요청
8. 의사결정 필요사항
9. 담당자와 기한
```

회의는 많지만 결정사항과 기록이 없다면 의사소통 체계가 작동하지 않는 것입니다.

## 8. 프로젝트 리스크관리: 발생 전의 불확실성을 관리한다

[![PMP 08 프로젝트 리스크관리 인포그래픽](/assets/images/pmp-08-risk.png)](/assets/images/pmp-08-risk.png)

*그림 8. 식별·분석·우선순위·대응·모니터링을 연결하는 리스크관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

리스크는 아직 발생하지 않았지만 프로젝트 목표에 긍정적 또는 부정적 영향을 줄 수 있는 불확실성입니다.

이미 발생한 문제는 리스크가 아니라 이슈입니다.

- 리스크: 중국 벤더가 약속한 시점에 iOS SDK를 제공하지 않을 수 있다.
- 이슈: 제공 예정일이 지났지만 iOS SDK가 전달되지 않았다.

리스크는 식별한 뒤 발생 가능성과 영향을 분석하고, 우선순위를 정하고, 대응계획과 담당자를 지정해야 합니다.

### 위협 대응전략

- 회피 Avoid
- 전가 Transfer
- 완화 Mitigate
- 수용 Accept
- 상향 Escalate

### 기회 대응전략

- 활용 Exploit
- 공유 Share
- 향상 Enhance
- 수용 Accept
- 상향 Escalate

리스크 등록부에는 다음 항목이 포함돼야 합니다.

- 원인
- 리스크 사건
- 예상 결과
- 발생 확률
- 영향도
- 대응전략
- 리스크 오너
- 대응 담당자
- 트리거
- 대응기한

모든 대응이 “지속 모니터링”으로 끝난다면 사실상 대응계획이 없는 것과 같습니다.

## 9. 프로젝트 조달관리: 외부 의존성을 계약 가능한 수준으로 구체화한다

[![PMP 09 프로젝트 조달관리 인포그래픽](/assets/images/pmp-09-procurement.png)](/assets/images/pmp-09-procurement.png)

*그림 9. Make-or-Buy·요구사항·공급업체·계약·성과통제를 연결하는 조달관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

조달관리는 프로젝트에 필요한 제품, 서비스, 결과를 외부에서 구매하거나 계약하고 공급 성과를 통제하는 영역입니다.

가장 먼저 해야 할 판단은 Make or Buy입니다.

핵심 기술을 내부에 축적해야 하거나 보안상 외부 위탁이 어렵다면 내부 수행이 적합할 수 있습니다. 반대로 특수 역량이 일시적으로 필요하거나 외부 업체가 더 빠르고 효율적이라면 외부 조달이 적합합니다.

스마트글래스·AI 프로젝트에서는 “SDK를 제공한다”는 말만으로 계약하면 위험합니다.

다음 항목을 조달문서와 계약서에 명확히 적어야 합니다.

- SDK 버전
- 지원 OS
- 지원 기능과 미지원 기능
- 샘플 앱 제공 여부
- 샘플 소스코드 제공 여부
- 기기·펌웨어·SDK 호환표
- 기술지원 범위
- 오류 대응시간
- 업데이트 정책
- OTA 지원 여부
- 소스코드 제공 여부
- 지식재산권
- 재배포 권한
- 검수 기준
- 종료 후 지원

조달 요청문서도 목적에 따라 구분해야 합니다.

- **RFI**: 시장과 공급업체의 가능성 탐색
- **RFQ**: 규격이 명확할 때 가격 견적 요청
- **RFP**: 요구사항에 대한 해결방안과 가격 제안 요청

조달 결과는 계약 체결로 끝나지 않습니다. 공급업체의 결과물을 일정, 품질, 호환성, 지원 수준과 연결해 지속적으로 통제해야 합니다.

## 10. 프로젝트 이해관계자관리: 명단이 아니라 지지와 참여를 만든다

[![PMP 10 프로젝트 이해관계자관리 인포그래픽](/assets/images/pmp-10-stakeholder.png)](/assets/images/pmp-10-stakeholder.png)

*그림 10. 이해관계자 식별·분석·참여전략·설득·조정을 연결하는 이해관계자관리 — 클릭하면 원본 크기로 볼 수 있습니다.*

이해관계자는 프로젝트에 영향을 미치거나 프로젝트 결과의 영향을 받는 사람, 집단, 조직입니다.

이해관계자관리는 명단 작성이 아닙니다.

> **프로젝트 성공에 필요한 지지, 승인, 참여와 의사결정을 확보하는 활동입니다.**

기업 AX 프로젝트에는 다음 이해관계자가 포함될 수 있습니다.

- 고객 임원
- 현업 부서장
- 현업 실무자
- IT팀
- 보안팀
- 법무팀
- 개인정보 담당자
- 구매팀
- 재무팀
- 개발팀
- 외부 벤더
- 최종 사용자
- 운영·유지보수 조직
- 정부기관 담당자
- 평가위원

특히 다음 역할을 구분해야 합니다.

### 스폰서

프로젝트를 후원하고 자원을 확보하는 사람입니다.

### 승인권자

범위, 예산, 변경, 검수 등을 공식 승인하는 사람입니다.

### 업무 책임자

현업 기준과 업무규칙을 결정하는 사람입니다.

### 최종 사용자

실제로 시스템을 사용하는 사람입니다.

### 통제 조직

보안, 법무, 개인정보, 구매처럼 사전 승인과 검토가 필요한 조직입니다.

Power-Interest Grid를 사용하면 영향력과 관심도에 따라 다음처럼 전략을 나눌 수 있습니다.

- 영향력 높음·관심도 높음: 밀착 관리
- 영향력 높음·관심도 낮음: 만족 유지
- 영향력 낮음·관심도 높음: 지속적인 정보 제공
- 영향력 낮음·관심도 낮음: 최소 수준 감시

또한 현재 참여수준이 Resistant인지, Neutral인지, Supportive인지 확인하고 목표 수준까지 변화시키는 계획이 필요합니다.

의사소통은 정보를 전달하는 것이고, 이해관계자관리는 상대가 이해하고 동의하고 실제 행동하게 만드는 것입니다.

## 10개 지식영역은 독립된 체크리스트가 아니다

프로젝트에서 하나의 변경요청이 발생하면 열 개 영역은 연쇄적으로 움직입니다.

```text
이해관계자
→ 고객 요구와 영향력 확인

의사소통
→ 요구의 목적과 조건 확인

범위
→ 포함·제외·산출물 분석

일정
→ 추가 기간과 의존성 분석

원가
→ 추가 비용 분석

자원
→ 인력·장비·가용성 확인

품질
→ 추가 검증기준 정의

리스크
→ 기술·일정 불확실성 분석

조달
→ 외부 벤더 필요성 검토

통합
→ 변경 승인·거절·보류
```

통합관리는 이 모든 정보를 종합해 최종 의사결정을 내리는 컨트롤타워입니다.

따라서 열 개 영역을 각각 운영하되, 실제 프로젝트에서는 서로 연결된 하나의 시스템으로 관리해야 합니다.

## Enterprise AX Playbook과 PMP 지식영역을 결합하는 방법

Enterprise AX Playbook은 기업의 업무에서 AI 기회를 발굴하고 검증하는 방법론입니다. PMP 지식영역은 그 일을 프로젝트로 계획하고 실행하고 통제하는 운영체계입니다.

```text
Enterprise AX Playbook
= 무엇을 발견하고 설계할 것인가

PMP Knowledge Areas
= 그 프로젝트를 어떻게 계획·실행·통제할 것인가
```

| Enterprise AX 단계 | 연결되는 핵심 PMP 지식영역 | 대표 산출물 |
|---|---|---|
| 01 현업 인터뷰 | 이해관계자·의사소통·범위 | 이해관계자 등록부, 인터뷰 계획, 요구사항 |
| 02 업무 분해 | 범위·통합·일정 | 범위기술서, WBS, 활동목록 |
| 03 데이터 확인 | 품질·리스크·자원·조달 | 데이터 목록, 품질기준, 접근 리스크 |
| 04 AI 적용성 평가 | 통합·품질·리스크 | 기술대안, 적용성 점수, 의사결정 기록 |
| 05 ROI 평가 | 원가·통합·이해관계자 | 원가산정, 비즈니스 케이스, 투자판단 |
| 06 PoC 설계 | 범위·일정·원가·품질·자원·리스크 | PoC 헌장, WBS, 일정, 예산, 평가계획 |
| 07 Human-in-the-loop | 품질·리스크·이해관계자·통합 | 승인매트릭스, 에스컬레이션, 감사로그 |
| 08 운영 KPI | 통합·품질·원가·일정·이해관계자 | 대시보드, 성과보고서, 개선 백로그 |

AX Playbook만 있으면 좋은 문제를 찾고 PoC를 설계할 수 있지만, 공식 권한, 변경통제, 예산, 자원, 계약, 검수와 종료가 약해질 수 있습니다.

반대로 PMP만 적용하면 프로젝트는 관리되지만, 어떤 AX 문제를 선택하고 어떤 AI 구조로 검증할지가 부족할 수 있습니다.

두 체계는 경쟁관계가 아니라 상호보완 관계입니다.

## 8~12주 AX·PoC 프로젝트에 필요한 최소 12개 문서

모든 프로세스를 무겁게 문서화할 필요는 없습니다.

중소규모 AX·PoC 프로젝트라면 다음 12개 산출물을 최소 운영체계로 사용할 수 있습니다.

| 번호 | 문서 | 반드시 포함할 내용 |
|---:|---|---|
| 1 | 프로젝트 헌장 | 목적·목표·스폰서·PM 권한·성공기준 |
| 2 | 이해관계자 등록부 | 역할·영향력·기대·참여전략 |
| 3 | 범위기술서 | 포함·제외·산출물·가정·제약 |
| 4 | 요구사항 추적표 | 요구사항·출처·구현·테스트·승인 |
| 5 | WBS | 프로젝트 전체 작업분해 |
| 6 | 일정 기준선 | 마일스톤·의존성·고객 제공 일정 |
| 7 | 원가 기준선 | 인건비·외주비·API·클라우드·예비비 |
| 8 | 품질·평가 계획 | 기술지표·업무지표·성공기준 |
| 9 | RACI | 수행자·책임자·협의자·통보대상 |
| 10 | 리스크·이슈 로그 | 확률·영향·대응·담당자·기한 |

| 12 | 검수·종료 보고 | 수용기준·인수·인계·교훈 |

이 문서들은 보고를 위한 서류가 아니라 프로젝트의 의사결정을 남기는 운영장치입니다.

문서를 만들고 사용하지 않는 것보다, 최소 항목으로 가볍게 만들고 주기적으로 갱신하는 편이 낫습니다.

## 마무리: PMP 10대 지식영역은 프로젝트의 운영체제다

PMP 10대 지식영역을 단순 암기목록으로 보면 실제 프로젝트와 연결하기 어렵습니다.

그러나 각각을 프로젝트가 반드시 답해야 하는 열 가지 질문으로 보면 강력한 운영체계가 됩니다.

```text
통합       전체를 맞춘다
범위       무엇을 할지 정한다
일정       언제 할지 정한다
원가       얼마를 쓸지 정한다
품질       어느 수준으로 만들지 정한다
자원       누가 무엇으로 할지 정한다
의사소통   정보를 어떻게 흐르게 할지 정한다
리스크     불확실성에 대비한다
조달       외부에서 무엇을 확보할지 정한다
이해관계자 지지와 승인을 확보한다
```

좋은 프로젝트관리는 모든 문서를 많이 만드는 것이 아닙니다.

필요한 의사결정을 제때 내리고, 그 결정이 범위, 일정, 원가, 품질, 자원과 리스크에 일관되게 반영되도록 만드는 것입니다.

특히 Enterprise AX 프로젝트에서는 **AX Playbook으로 올바른 문제를 발견하고**, **PMP 지식체계로 그 문제를 안정적으로 실행·통제하는 구조**가 필요합니다.

이 두 체계가 결합될 때 PoC가 단순한 데모로 끝나지 않고 실제 운영과 확산으로 이어질 가능성이 높아집니다.
